# خطة تطوير RED المحلية الشاملة

## الهدف

تطوير مشروع **RED** المحلي القائم، وليس إعادة بنائه من الصفر، ليصبح منصة عربية متكاملة للرسائل والاتصالات والمجموعات والمنشورات والحالات والبث والمؤتمرات. يشمل ذلك تطبيق Android/Kotlin/Compose وخادم Spring Boot/Kotlin ولوحة الإدارة React/TypeScript وAsterisk وتكامل بوابة DINSTAR UC2000-VE لمكالمات PSTN وSMS، مع الحفاظ على بيانات الهواتف وإعدادات البوابة الحالية.

> لا تُعتبر أي ميزة مكتملة لمجرد وجود واجهة لها. يلزم لكل ميزة تدفق مستخدم فعلي، نموذج بيانات وصلاحيات، ربط خادم، اختبارات، وحالة خطأ/إعادة محاولة قابلة للفهم.

## قرارات معمارية

| المجال | القرار |
|---|---|
| Android | الاحتفاظ بـ Kotlin وJetpack Compose وWebRTC الحاليين، ثم توحيد state management وطبقات ViewModel/Repository وواجهات RTL تدريجياً. |
| الخادم | الاحتفاظ بـ Spring Boot/Kotlin وDocker Compose؛ تقوية API وWebSocket والمراقبة وmigrations بدلاً من الاستبدال الكامل. |
| لوحة الإدارة | تطوير لوحة React/TypeScript الحالية لتشمل الإشراف والتشغيل وإدارة المحتوى والمكالمات وSMS وتقارير الأعطال. |
| رسائل ومكالمات 1:1 | WebSocket أساسي، FCM ثم pending HTTP كاحتياط؛ `callId` وmessage ID idempotent لمنع التكرار. مكالمات 1:1 تبقى P2P WebRTC مع TURN. |
| غرف وبث ومؤتمرات | لا تستخدم P2P mesh. يُنفذ POC لخادم SFU منفصل (LiveKit أو mediasoup) ثم يعتمد واحد فقط بعد اختبار حقيقي للحمل والجودة. |
| البث | بث، دردشة، ضيوف، إشراف، تقارير وإحصاءات؛ **من دون هدايا أو عملات أو دفع**. |
| DINSTAR | يُعزل في adapter لخدمات SIP/Asterisk وSMS HTTP API/SMPP. لا تعديل حي للإعدادات قبل لقطة read-only واختبار غير مؤثر. |
| البيانات | offline-first للرسائل وسجل المكالمات والـoutbox عبر تخزين محلي مشفر ومزامنة قابلة لإعادة المحاولة. |
| التصميم | نظام تصميم واحد عربي RTL للألوان والخطوط والحالات والوصولية؛ لا تنشأ شاشات أو أزرار منفصلة خارج النظام. |

## المرحلة 1: فهرسة شاملة وخط أساس

يُفهرس التطبيق والخادم ولوحة الإدارة والـDocker وقاعدة البيانات ومسارات الإشارات والمكالمات والوسائط وDINSTAR. ينفذ خط أساس يشمل Android build/tests، Backend tests/health، فحص لوحة الإدارة، Docker health، وحالة شبكة وأذونات الهاتفين. يسجل كل عيب بدليل قابل لإعادة الإنتاج، خطورة، مكوّن متأثر، وخطة إصلاح.

| مخرج | معيار القبول |
|---|---|
| خريطة الميزات | كل شاشة وخدمة وAPI وجدول يصنف: مكتمل، جزئي، غير موصول، أو معطّل. |
| سجل العيوب | خطوات إعادة إنتاج وسجل داعم وأولوية لكل عيب. |
| تقرير صحة | build/test/health محفوظة من دون تغيير بوابة DINSTAR. |

## المرحلة 2: المعمارية والأمن والجودة

تُوحد عقود DTO وواجهات الإشارات، وتراجع migrations والفهارس وسلامة المرجعيات. يُضاف correlation ID وstructured logging وhealth/metrics، مع حجب الأسرار والبيانات الشخصية. في Android تُراجع صلاحيات الكاميرا والميكروفون والإشعارات، foreground service للمكالمات، certificate pinning، WorkManager، Room، وعمليات المزامنة. لا تُرقى المكتبات لمجرد حداثتها؛ تنشأ مصفوفة توافق Kotlin/AGP/Compose/WebRTC/Spring/React ثم ترقية تدريجية قابلة للرجوع.

## المرحلة 3: نظام التصميم والتنقل العربي

يُنشأ design system رسمي موحد: tokens للألوان والخلفيات والحدود والحالات، تدرج طباعي عربي قابل للقراءة، مساحات لمس مناسبة، دعم RTL، واجهات loading/error/empty، وأوصاف وصول. يعاد ترتيب التنقل الرئيسي إلى: الدردشات، المكالمات، المجتمعات، الاستكشاف/المنشورات، الحالات، البث، والإعدادات.

| السطح | التحسين |
|---|---|
| الدردشة والمكالمات | أزرار صوت وفيديو منفصلة وموسومة، رنين واحد، إنهاء واضح، وحالة اتصال مفهومة. |
| القوائم | Paging، بحث وفلاتر، مؤشرات مزامنة، واستعادة حالة التنقل. |
| الهوية | لوحة RED داكنة/فاتحة متناسقة وخط عربي رسمي بعد فحص الترخيص والمقاييس. |
| الإشعارات | قنوات واضحة وdeep links صحيحة، من دون فتح واجهات واردة مكررة. |

## المرحلة 4: المحادثات الخاصة والرسائل الصوتية والوسائط

تتحول المحادثات إلى offline-first: outbox محلي مشفر، إرسال idempotent، حالات موحدة (محلي/قيد الإرسال/أرسل/وصل/قُرئ/فشل)، retries ومصالحة عند الاتصال. تشمل الصورة والفيديو والملفات والموقع والردود والتفاعلات والتحرير والحذف والبحث والوسائط المؤقتة.

تستكمل الرسائل الصوتية بملف متوافق، waveform، تشفير وmanifest، تنزيل وفك تشفير آمن، ExoPlayer ثابت، تقدم وسرعة تشغيل، وإدارة audio focus. لا تغلق الدفعة قبل اختبار التسجيل والإرسال والتشغيل الطويل على جهازين.

## المرحلة 5: المكالمات الفردية الصوتية والفيديو

تُفصل مكالمتا الصوت والفيديو في واجهة البدء والحالات وإعداد الوسائط، مع shared signaling واضح. يُراجع SDP وICE/TURN وaudio routing وcamera tracks وforeground lifecycle والإغلاق. لا يسمح OFFER نفسه الوارد من WebSocket وFCM وpending HTTP بإنشاء أكثر من رنة أو واجهة أو `PeerConnection`.

| السيناريو | اختبار القبول |
|---|---|
| صوت 1:1 | بدء سريع، رنين واحد، قبول، كتم/سماعة، إنهاء بلا تعليق أو خروج، ثم مكالمة ثانية. |
| فيديو 1:1 | أذونات، معاينة محلية، صوت وفيديو بعيدان، تبديل كاميرا، إطفاء كاميرا يستمر معه الصوت، واستعادة ICE. |
| خلفية وقفل | إشعار أو واجهة واحدة فقط، قبول/رفض صحيح، وعدم تضاعف الإشارة. |
| الجودة | قياس OFFER→RINGING→ANSWER وRTT/jitter/loss مع سجلات تشخيص لا تسرب بيانات. |

## المرحلة 6: المجموعات والمجتمعات

تتحول المجموعات إلى أدوار وصلاحيات قابلة للتدقيق: مالك، مدير، مشرف، عضو، مقيد، ومدعو. تشمل الإعلانات والمواضيع والاستطلاعات والوسائط والبحث والدعوات وقائمة الأعضاء وسجل الإدارة والحظر والبلاغات. يبقى مفهوم مجموعة المحادثة منفصلاً عن غرفة المكالمة الجماعية.

## المرحلة 7: المكالمات الجماعية والمؤتمرات

ينشأ POC منفصل لخادم SFU يتضمن رموز قصيرة العمر، غرف، ناشرين ومشتركين، TURN، quality adaptation، مشاركة شاشة عندما تسمح Android، محادثة، قائمة مشاركين، يد مرفوعة، غرفة انتظار، قفل غرفة، كتم المضيف وموافقة تسجيل. بعد اختبار حمل محلي واقعي يعتمد SFU واحد فقط.

تقدم المؤتمرات تجربة غرف/مساحات مستقلة: مستمعون ومتحدثون، طلب تحدث، إشراف، موضوع وجدولة، إعادة دخول، وإبلاغ. لا ترتبط بمجموعة إلا بدعوة أو رابط صريح.

## المرحلة 8: البث المباشر بلا هدايا

يبنى البث كمنتج مستقل: استوديو مضيف، عنوان وخصوصية، معاينة، ضيوف ضمن SFU، دردشة، تفاعلات غير مالية، تثبيت رسالة، قائمة مشرفين، mute/ban/report، جودة وإحصاءات، إنهاء منظم، وmetadata أو replay وفق الموافقة وسياسة الاحتفاظ. تستبعد الخطة الهدايا والعملات والمدفوعات تماماً.

## المرحلة 9: المنشورات والحالات والأصدقاء

يعتمد feed على شبكة **أصدقاء** وخصوصية منشور (أصدقاء/عام/مخصص) بدلاً من المتابعين كافتراض. يشمل مسودات ووسائط وتفاعلات وتعليقات وحفظ ومشاركة وإبلاغ وبحث. تُبنى الحالات كقصص مؤقتة بسياسة مدة ومشاهدة وردود وخصوصية وحذف واضح.

## المرحلة 10: DINSTAR UC2000-VE وPSTN وSMS

يُبنى adapter مستقل: SIP/Asterisk للمكالمات وHTTP API/SMPP للرسائل وفق ما هو مفعل فعلياً في البوابة. يبدأ العمل بلقطة إعدادات read-only، اختبار trunk وAMI والقنوات وCDR، ثم outbox server-side للـSMS بحالات قبول/إرسال/تسليم/فشل، retries وrate limits وinbound SMS وmapping للـSIM/port. لا تتغير SIMs أو routing أو dial plan الحية من دون موافقة منفصلة.

> توفر DINSTAR HTTP API للـSMS وأدلة UC2000-VE الرسمية؛ يُتحقق من الإصدار والخصائص المفعلة قبل أي تكامل إنتاجي. [1] [2]

## المرحلة 11: الخادم ولوحة الإدارة وقاعدة البيانات

تستكمل migrations والفهارس وoptimistic locking وsoft deletion حيث يلزم وaudit logs وسياسات retention. تضاف لوحات لإدارة الهوية والأصدقاء والمجموعات والمنشورات والحالات والبلاغات والمكالمات والبث والرسائل وDINSTAR/SMS. تشمل RBAC وقياسات تشغيل وصفوف فشل قابلة لإعادة المحاولة وتأكيداً ثنائياً للعمليات الحساسة.

## المرحلة 12: الاختبارات والأمن والإطلاق التدريجي

لكل نطاق اختبارات unit وcontract وintegration ثم اختبار جهازين. تتضمن smoke suite: دخول، بحث، دردشة، مرفق، رسالة صوتية، صوت، فيديو، مجموعة، منشور، حالة وإشعار. تراجع حماية البيانات المحلية، tokens، الصلاحيات، rate limits، عدم تسريب الأسرار، وتدفقات report/block/moderation المطلوبة للمحتوى الذي ينشئه المستخدم.
