## الخلاصة التنفيذية

المستودع ليس مشروع واجهة واحدًا؛ بل منصة Android محلية أولًا مع خادم Kotlin/Spring، لوحة إدارة React/Vite، طبقة SFU مبنية على Node/mediasoup، وعقود Protobuf مشتركة. توجد بنية واسعة ووثائق كثيرة، لكن **حالة البناء الحالية لا تسمح باعتبار التطبيق جاهزًا لتطوير ميزات جديدة**: ترجمة تطبيق Android تفشل داخل `RedDashboard.kt`، وأمر اختبار الخادم الموثق لا يعمل لأن الخادم غير مشمول في إعداد Gradle الجذري، وتشغيل التكامل الكامل لا يمكن التحقق منه في بيئة التدقيق لعدم وجود Docker.

> قرار التنفيذ: تبدأ أعمال المنتج بإصلاح قابلية البناء وبنية المشاريع والعقود الحالية، ثم تنفيذ نظام التصميم والميزات الجديدة فوق أساس قابل للاختبار. لا تُزال أو تُعاد كتابة طبقة التشفير أو بروتوكول الرسائل الخاصة دون نموذج تهديد ومراجعة مستقلة.

| النتيجة | الحالة | أثرها على التطوير |
|---|---:|---|
| اكتشاف مشروع Gradle الجذري | ناجح | المشروع الجذري يضم `:app` و`:shared-proto` فقط. |
| ترجمة Android واختبارات وحدته | فاشل | توجد أخطاء Kotlin/Compose فعلية تمنع إنتاج APK أو تشغيل اختبارات الوحدة التابعة له. |
| فحص لوحة الإدارة | ناجح | عقد API وحراس الواجهة والأدوار وفحص TypeScript نجحت. |
| فحص صياغة SFU | ناجح بتحفظ | فحص JavaScript نجح، لكن بيئة Node المستخدمة أقل من الحد المعلن في الحزمة. |
| اختبار الخادم الموثق | فاشل | الأمر الموثق يشير إلى مشروع Gradle غير مسجل في الإعداد الجذري. |
| تشغيل Docker المتكامل | غير منفذ | Docker غير موجود في بيئة التدقيق. |

## نتائج التحقق التفصيلية

### 1. Gradle وتطبيق Android

أمر `./gradlew projects` نجح وأثبت أن الرسم الحالي يضم مشروعَي `:app` و`:shared-proto` فقط. بعد تهيئة JDK وSDK شغّل التدقيق:

```text
./gradlew :app:compileDebugKotlin :app:testDebugUnitTest
```

انتهى الأمر بالفشل في مهمة `:app:compileDebugKotlin`. ظهرت أخطاء فعلية داخل `red-app/src/main/java/com/red/sovereign/ui/RedDashboard.kt`، منها مراجع غير محلولة مثل `QuickReply` و`Copy` و`openPrivateChat`، واستدعاءات `@Composable` خارج سياق Composable، واستخدام غير صحيح لـ `Surface`، وعدم تطابق أنواع، وتسلسلات هروب غير مدعومة. لأن مرحلة الترجمة تفشل، لا يمكن اعتبار اختبارات وحدة التطبيق منفذة حتى تصل المهمة إليها.

| الأولوية | الإجراء المطلوب | معيار القبول |
|---|---|---|
| P0 | تصنيف أخطاء `RedDashboard.kt` إلى مراجع مفقودة، نطاق Composable، وواجهات مكونات غير صحيحة. | نجاح `:app:compileDebugKotlin` بلا أخطاء. |
| P0 | فصل الواجهة الضخمة إلى شاشات ومكونات وطبقات حالة اختبارية بدل زيادة الملف المركزي. | كل تدفق رئيسي له مكون ومسار حالة واضحان. |
| P0 | إعادة تشغيل اختبارات الوحدة بعد نجاح الترجمة. | نجاح `:app:testDebugUnitTest` وإرفاق التقرير. |
| P1 | إضافة اختبارات واجهة ومسارات RTL والخصوصية والتنقل. | نتائج قابلة للتكرار في CI. |

### 2. الخادم وبنية Gradle

تقول وثائق الجذر إن أمر الاختبار هو `./gradlew :backend-server:test`، لكن `settings.gradle.kts` لا يضم `:backend-server`. لذلك يفشل الأمر قبل تنفيذ أي اختبار برسالة أن المشروع `backend-server` غير موجود. في الوقت نفسه يستورد `backend-server/build.gradle.kts` البروتوكول عبر `implementation(project(":shared-proto"))`، ما يثبت أن الخادم والتطبيق يحتاجان نموذج بناء موحدًا أو إعدادًا مركبًا موثقًا بوضوح.

| الفجوة | المخاطرة | الإصلاح المخطط |
|---|---|---|
| الخادم خارج إعداد Gradle الجذري | لا توجد بوابة موثوقة تبني الخادم والبروتوكول معًا. | اعتماد مشروع متعدد الوحدات صريح، أو composite build مضبوط مع اختبار مستقل موثق. |
| أمر README غير صالح حاليًا | يعيق المطورين وCI ويعطي نتيجة وهمية عن الجودة. | استبدال الأوامر بتعليمات تعمل فعليًا وإضافة فحص CI إلزامي. |
| عقود API عديدة مقابل واجهات متعددة | خطر انحراف العميل واللوحة والخادم. | توليد/التحقق من العقود من مصدر واحد ودمجه في بوابة الجودة. |

### 3. لوحة الإدارة

تم تنفيذ `npm ci` ثم `npm run check` داخل `admin_dashboard`. نجحت سلسلة الفحوص: تحقق عقد API، حراس الواجهة، تطابق الأدوار، وفحص TypeScript. أعطى فاحص العقد نتيجة مرئية: `124` استدعاء واجهة مقابل `317` مسار خادم، ولم يسجل فشلًا في العملية الحالية. أبلغ تثبيت الحزم عن **ثغرة عالية واحدة** وفق قاعدة بيانات npm وقت الفحص؛ يلزم تشخيصها بعملية تدقيق مقيدة، وليس تطبيق `npm audit fix` عشوائيًا لأنه قد يغير الإصدارات أو يكسر الحزمة.

| القرار | التنفيذ |
|---|---|
| الحفاظ على النجاح الحالي | لا يعاد تصميم لوحة الإدارة قبل استخراج مكونات قابلة لإعادة الاستخدام وتغطية المسارات الحساسة. |
| معالجة الثغرات | تحديد الحزمة المتأثرة، مسار الوصول، وإصدار الإصلاح المتوافق؛ ثم اختبار البناء والفحوص. |
| تعزيز الإدارة | بناء وحدات الصلاحيات والتدقيق والإشراف والنسخ الاحتياطي والقياسات فوق العقود الموجودة، لا فوق بيانات وهمية. |

### 4. طبقة SFU ووسائط الاتصال

تم تنفيذ `npm ci` و`npm run check` داخل `media-sfu` ونجح فحص JavaScript. مع ذلك تصف الحزمة `red-media-sfu@2.0.0` حد محرك واضحًا هو Node `>=24`، بينما بيئة التدقيق وفرت Node 22.13.0؛ سجل npm تحذير توافق لا يمنع فحص الصياغة لكنه يمنع الحكم على جاهزية التشغيل الفعلي. كما ظهر تنبيه npm عن ثغرة عالية واحدة، ويجب تحليلها وتحديثها بعد توافق Node.

| قرار الوسائط | السبب | خطوة التحقق |
|---|---|---|
| عدم استبدال SFU في هذه الدفعة | توجد طبقة mediasoup فعلية تحتاج اختبارًا قبل الحكم عليها. | تثبيت Node 24+، تشغيل SFU ضمن Compose، فحص health، وقياس مكالمة بين جهازين. |
| عزل منتجات الاتصال | المكالمة الفردية، الغرفة الجماعية المستقلة، المؤتمر الصوتي، والبث العام لها سياسات وصلاحيات وحالات مختلفة. | عقود غرف مستقلة وواجهات منفصلة، لا ربط قسري بالمجموعات. |
| عدم إضافة هدايا للبث | هذا شرط منتج صريح. | لا تُضاف جداول عملات/هدايا/إكراميات أو واجهات لها. |

## القرار التقني للمرحلة التالية

لا يبدأ توسيع المحادثات أو المجموعات أو المنشورات أو المكالمات قبل إغلاق ثلاث بوابات P0: **قابلية ترجمة Android، قابلية بناء الخادم من المسار الموثق، وبيئة تشغيل يمكنها فحص التكامل.** بعد ذلك يبنى نظام التصميم العربي الرسمي فوق مكونات Android منظمة، ثم تتطور البيانات والعقود والميزات تدريجيًا مع اختبارات مرافقة.

التسجيل الحالي مبني على RED ID وموافقة إدارة، لا على رقم هاتف أو SMS/OTP. لذلك لن يحول هذا البرنامج مسار إنشاء الحساب إلى SMS دون مواصفة موافق عليها ونموذج خصوصية وإساءة استخدام. يمكن تصميم تكامل SMS اختياري لاحقًا لإشعارات إدارية/تسليمات مسموحة، لكن لا يوضع مفتاح مزود أو رقم إنتاجي في Git أو في التطبيق.

## تحديث التنفيذ — استعادة ترجمة Android

بعد فتح طلب الدمج المسودة، عولجت **138** مشكلة ترجمة Kotlin/Compose متراكمة على دفعات صغيرة، مع إعادة تشغيل بوابة الترجمة بعد كل مجموعة. شملت الإصلاحات مواءمة واجهات Compose وMaterial، تدفقات التخزين المشفر، عميل الوسائط، حالة البحث المحلي، Android Telecom وWebRTC، إشارة Protobuf، وإصلاحات عزلية ضرورية لاستعادة تجميع الوحدات الموجودة. لم يُطوَّر أو يُربط أي جهاز هاتف يمني أو DINSTAR؛ اقتصر ما مس هذه الوحدة على اعتماد/استيراد مطلوبين كي لا تمنع الشيفرة الموجودة بناء التطبيق.

| بوابة التحقق | النتيجة بعد الإصلاح | الدليل |
|---|---:|---|
| ترجمة Kotlin لتطبيق Android | **ناجح** | `:app:compileDebugKotlin` انتهت بـ `BUILD SUCCESSFUL` في 1 دقيقة و22 ثانية، بلا أخطاء ترجمة. |

### تحديث بوابة الخادم

تبيّن أن الخادم يملك إعداد Gradle مستقلًا صحيحًا في `backend-server/settings.gradle.kts` يضم `../shared-proto`. كان العطل في أمر التوثيق الذي استدعاه من جذر Android. الأمر الموثوق المعتمد للخادم هو:


## دفعة التحصين: تخصيص منافذ PSTN ومكالماتها دائم — 19 أغسطس 2026
استُبدل عداد استخدام منفذ DINSTAR المتقلب داخل JVM بحجز ذري في PostgreSQL (`gateway_port_reservations`). يختار الموزع منفذًا صالحًا ثم ينشئ حجزًا له بمهلة 15 دقيقة عبر قيد فريد، فلا تستطيع عقدة خادم ثانية أو إعادة تشغيل العملية اعتبار المنفذ نفسه متاحًا خطأً. يتحرر الحجز idempotently عند hangup أو عند رصد المنفذ خاملًا، وتزيل مهمة دورية الحجوزات منتهية المهلة فقط.

كما نُقلت علاقة `callId → ownerRedId/gateway/port` من JVM إلى جدول `pstn_active_calls`. ينشأ معرف ارتباط UUID واحد قبل originate، ويسجل في PostgreSQL وAMI وسجل المكالمات، فتظل صلاحية hangup وتحرير المنفذ قابلة للاسترجاع بعد restart. بقي سجل قرارات التوجيه والتحقق من الإشارة ومطابقة مشغلي اليمن كما هو.

**التحقق:** نجحت اختبارات الخادم كاملة عبر `./gradlew -p backend-server test`، وحُدّث اختبار حد المكالمات اليومي ليتحقق من عدم إجراء أي اتصال Asterisk. عند `DINSTAR_ENABLED=false` يرفض مسار dial قبل لمس قاعدة البيانات أو Redis أو Asterisk، ويعرض `/api/pstn/status` الحالة `HARDWARE_DISABLED` بدل ادعاء أن المسار نشط. يلزم اختبار عتاد حي منفصل لبداية/نهاية مكالمة عبر بوابة مصرح بها قبل إعلان مسار PSTN المادي جاهزًا إنتاجيًا.
