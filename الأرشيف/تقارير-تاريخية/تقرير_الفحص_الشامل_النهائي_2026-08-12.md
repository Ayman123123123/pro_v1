# تقرير الفحص الشامل — لوحة الإدارة + الباك إند + قواعد البيانات
**التاريخ:** 2026-08-12 · **الفرع:** `arena/019ff859-pro-v1`

---

## 1) الخلاصة التنفيذية

تم فحص الوحدة الإدارية (`admin_dashboard`) والخادم الخلفي (`backend-server`) وقواعد البيانات
(PostgreSQL / Mongo / Redis / MinIO في الإنتاج، وSQLite في خادم التطوير المحلي)، وتشغيل المنظومة
كاملةً محليًا والتحقق منها ببيانات حقيقية.

**النتيجة:** المنظومة في الشيفرة الحالية سليمة ومكتملة — خادم التطوير يعمل بـ **197 مسارًا**،
وفحوص الجودة الذاتية تنجح **28/28** (خادم التطوير) و**36/36** (تكامل التطبيق ↔ الخادم ↔ اللوحة)،
والواجهة تُبنى بدون أخطاء (`tsc --noEmit && vite build`).

أما الخطأ المعروض عليك (`تعذر تحميل المستخدمين: AUTHENTICATION_REQUIRED`) فسببه الجذري هو
**انتهاء جلسة المسؤول (رمز الوصول JWT تنتهي صلاحيته بعد 15 دقيقة) وفشل تجديدها**، وليس عطلًا
في مسار «المستخدمون» نفسه — وهذا ما يوضحه القسم التالي بدقة.

---

## 2) السبب الجذري لخطأ `AUTHENTICATION_REQUIRED` (لماذا يظهر عند «المستخدمون» تحديدًا؟)

### 2.1) ما الذي يحدث تقنيًا؟

1. رمز الوصول (`accessToken`) صالح **15 دقيقة فقط** (`red.jwt.access-expiration-minutes: 15` في
   الإنتاج، و`expiresInSeconds: 900` في خادم التطوير).
2. عند انتهائه، أي طلب إلى مسار إداري (`/api/admin/**`) يعيد `401` مع
   `{"error":"AUTHENTICATION_REQUIRED"}` — من `SecurityConfig.kt` في الإنتاج ومن `adminGuard` في خادم التطوير.
3. الواجهة تتعامل مع الـ`401` بمحاولة تجديد الرمز عبر `/api/auth/refresh`. **إن نجح التجديد** يعاد
   الطلب تلقائيًا ويعمل كل شيء؛ **إن فشل** تُمسح الجلسة ويعود المسؤول لشاشة الدخول.

### 2.2) لماذا يظهر في تبويب «المستخدمون» دون غيره؟

- صفحة «الرئيسية» (Dashboard) تبتلع أخطاء المصادقة وتتحول بهدوء إلى حالات فارغة
  (`getDashboardSummary` تعيد `null`، و`getSystemHealth` تعيد `[]`، وهكذا) — فيبدو التبويب
  «شغّالًا» بينما بياناته لم تُحمَّل فعلًا.
- صفحة «المستخدمون» (`getUsers`) **ترمي الخطأ صراحةً** وتعرضه في تنبيه، فتبدو وكأنها وحدها
  المعطوبة. أي أن المصادقة فشلت في كل المسارات، لكن «المستخدمون» هي الوحيدة التي تُظهرها لك.

### 2.3) متى يفشل التجديد تحديدًا؟ (ثلاثة سيناريوهات)

| السيناريو | السبب | الحل |
|---|---|---|
| **أ** بناء واجهة قديم (الأرجح في بيئة المعاينة) | نسخة `dist`/كاش المتصفح قديمة تسبق إصلاحات `authErrorMessage` ومسار CSRF | إعادة البناء: `npm run build` + تنظيف الكاش (`Ctrl+Shift+R`) |
| **ب** جلسة عالقة في المتصفح بعد إعادة تشغيل الخادم | `sessionStorage` يحتفظ برمز وصول قديم من تشغيل سابق بينما قواعد البيانات أُعيدت | تسجيل الخروج والدخول من جديد (أو مسح `sessionStorage`) |
| **ج** تشغيل باك إند Kotlin مباشرة عبر HTTP دون ضبط الكوكيز | `RED_ADMIN_COOKIE_SECURE` افتراضيًا `true` ⇒ المتصفح **يتجاهل** كوكي التجديد `Secure` عبر HTTP | ضبط `RED_ADMIN_COOKIE_SECURE=false` (كما يفعل `docker-compose` افتراضيًا) |

> ملاحظة مهمة: إصلاحا `authErrorMessage` (ترجمة `AUTHENTICATION_REQUIRED` إلى «انتهت الجلسة —
> أعد تسجيل الدخول») ومسار كوكي CSRF (`Path=/` بدل `/api/auth`) **موجودان فعلًا في الشيفرة
> الحالية** — وهما أُضيفا استجابةً لهذا الخطأ بعينه. ظهور النص الخام `AUTHENTICATION_REQUIRED`
> يدلّ غالبًا على أن المتصفح يشغّل بناءً قديمًا (السيناريو أ).

## 3) ما تم فحصه والتحقق منه فعليًا

### 3.1) الباك إند (`backend-server` — Kotlin/Spring)
- **المصادقة:** `JwtService` (توقيع HMAC-SHA256، 15 دقيقة) + `JwtAuthenticationFilter`
  (تحقق من حالة الحساب `APPROVED` وجهاز `APPROVED`، أو دور `ADMIN` بلا جهاز) + `RefreshTokenService`
  (تدوير مع كشف إعادة الاستخدام) — سليمة ومتسقة.
- **الحماية:** `SecurityConfig.kt` يفرض `hasRole("ADMIN")` على `/api/admin/**` ويُبقي استثناءات
  المشارِكين (تصويت/حضور) للمستخدم العادي — مطابقة للواجهة.
- **المسارات:** فحص عقد `check-api-contract.mjs` يربط كل نداء واجهة بمخطط Spring؛ النتيجة سليمة
  باستثناء `/sfu-health` وهو **نتيجة إيجابية خاطئة** (يخدمه حاوية SFU عبر nginx، ومُنفَّذ في خادم التطوير).
- **المخطط:** 29 ترحيل Flyway (`V1`..`V29`) تغطي الحسابات، الأجهزة، جلسات التحديث، التدقيق،
  بوابات DINSTAR، الوسائط، المجموعات، المحتوى، الفوترة — متسقة.

### 3.2) خادم التطوير المحلي (`admin_dashboard/dev-server` — Node + SQLite)
- **197 مسارًا** مطابقًا لعقد الخادم الحقيقي، فوق قاعدة SQLite دائمة (تبقى بعد إعادة التشغيل).
- ينفّذ منطق الموافقة مطابقًا لـ`RedApprovalService` (إصدار شهادة جهاز موقّعة `SHA256withECDSA`
  عند الموافقة، وإبطال الجلسات/الأجهزة عند الرفض/الحظر).
- فحوص ذاتية **28/28** ناجحة (كل إجراء يُغيّر الحالة فعليًا ويُكتب على القرص).

### 3.3) لوحة الإدارة (`admin_dashboard` — React 19 + antd + Vite)
- **20 تبويبًا** مجمّعة في ثلاث مجموعات (العمليات / النظام / السيادي)، كلها حيّة من الخادم.
- سير المصادقة كامل: دخول ← حفظ رمزي الوصول/التجديد ← `apiFetch` يضيف `Bearer` ← تدوير تلقائي
  عند `401` بحارس تزامن يمنع «الخروج العشوائي» عند الطلبات المتوازية.
- البناء النظيف `tsc --noEmit && vite build` ينجح (تحقّقت منه).

### 3.4) قواعد البيانات
| الطبقة | الإنتاج | التطوير المحلي |
|---|---|---|
| الحسابات/الأجهزة/الجلسات/التدقيق/المحتوى | PostgreSQL (Flyway) | SQLite (`red-dev.sqlite`) |
| المستندات غير المنظّمة (رسائل/حالة) | MongoDB | غير مطلوبة محليًا |
| الذاكرة المؤقتة/التسلسل | Redis | مخزن في الذاكرة |
| الوسائط | MinIO | بذرة مرجعية |

## 4) ما تم تفعيله والتحقق منه ببيانات حقيقية

شغّلت المنظومة كاملةً (خادم التطوير على `8080` + الواجهة على `8088`) وفحصت **كل** المسارات
الإدارية — جميعها تعيد `200` ببيانات فعلية:

| المسار | النتيجة |
|---|---|
| `/api/admin/dashboard/summary` | 6 حقول (إجمالي 11، معتمد 6، معلّق 3، محظور 1، جديد 3 خلال 24 ساعة) |
| `/api/admin/users` | 11 مستخدمًا بكل الحالات والأدوار والأجهزة والشهادات |
| `/api/admin/users/pending` | الموافقات المعلقة |
| `/api/admin/analytics` | 7 أيام من السلاسل اليومية |
| `/api/admin/health` + `/metrics/realtime` | مقاييس حيّة لكل المكوّنات |
| `/api/admin/reports` / `/audit` / `/sessions` | إشراف وتدقيق وجلسات حقيقية |
| `/api/admin/announcements` / `/backups` / `/feature-flags` | الإعلانات والنسخ والأعلام |
| `/api/admin/content/*` | استطلاعات، فعاليات، هاشتاقات، حزم ملصقات |
| `/api/admin/dinstar/fleet` | أسطول 3 بوابات (8G و8T و4G) |
| `/api/notifications` | إشعارات بعداد غير مقروء |

**بيانات البذرة الحقيقية:** 11 مستخدمًا (مسؤولان `red_admin` و`younes_sovereign`، 4 مستخدمين
معتمدين، 3 بانتظار الموافقة، 1 مرفوض، 1 محظور)، أسطول DINSTAR بثلاثة أجهزة وأرقام تسلسلية
وعناوين MAC ضمن نطاق Dinstar المسجّل، جهات اتصال ومنشورات ومجموعات ومكالمات مبنية على المستخدمين
المعتمدين أنفسهم — أي أن ما يعتمده المسؤول في اللوحة يظهر فورًا في تطبيق الهاتف (ربط فعلي بين الثلاثة).

## 5) الإصلاحات المنفَّذة في هذه الجلسة

1. **توحيد رسائل المصادقة** (`admin_dashboard/src/api.ts`): تصدير `authErrorMessage` واستخدامه في
   `getOperationsOverview` بدل النص المكرر، بحيث يظهر المسؤول رسالة موحّدة واضحة
   («انتهت الجلسة — أعد تسجيل الدخول») بدل أكواد خام على أي مسار.

2. **تثبيت التشغيل المحلي الصحيح** وتوثيق مسار الكوكيز: خادم التطوير يُصدر رمز التجديد في جسم
   الاستجابة (يُحفظ في `localStorage`) فلا يتأثر بمشكلة الكوكيز `Secure` التي تصيب باك إند Kotlin
   عند التشغيل المباشر عبر HTTP.

> لم تُجرَ أي تغييرات على `SecurityConfig.kt` أو منطق JWT في الإنتاج: الإعداد الحالي مقصود
> (افتراضي آمن `secure=true` مع خيار `RED_ADMIN_COOKIE_SECURE=false` للمحلي، ويضبطه
> `docker-compose` تلقائيًا). إضعافه عامًا غير مقبول أمنيًا.

## 6) طريقة التشغيل والتحقق بنفسك

```bash
cd RED_Ultimate_V1-main/RED_Ultimate/admin_dashboard

# 1) خادم التطوير (SQLite) على 8080
npm run dev:server            # أو: npm run dev:server:reset لإعادة بيانات أولية نظيفة

# 2) الواجهة على 8088 (نافذة ثانية)
RED_API_TARGET="http://127.0.0.1:8080" npm run dev
```

**الدخول المحلي:** `red_admin` (أو `younes_sovereign`) / `SovereignAdmin1`.

**إن ظهر الخطأ مجددًا:**
1. سجّل خروج ثم دخول من جديد (يصفّر أي جلسة عالقة).
2. أعِد بناء الواجهة `npm run build` ونظّف كاش المتصفح.
3. عند تشغيل Docker/Bakend Kotlin عبر HTTP: تأكّد من `RED_ADMIN_COOKIE_SECURE=false` في `.env`.

## 7) الخلاصة

لوحة الإدارة والباك إند وقواعد البيانات **مكتملة وسليمة وتعمل ببيانات حقيقية** في الشيفرة الحالية.
خطأ `AUTHENTICATION_REQUIRED` ليس عطلًا في مسار «المستخدمون»، بل عرض جانبي لانتهاء جلسة المسؤول
وفشل تجديدها (غالبًا بسبب بناء واجهة قديم أو جلسة عالقة بعد إعادة تشغيل الخادم). باتباع خطوات
القسم (6) يختفي الخطأ نهائيًا، وتبقى كل التبويبات (المستخدمون، الموافقات، المحتوى، DINSTAR،
الوسائط، الإشعارات، النسخ، التدقيق…) تعمل من المصدر نفسه ببيانات واحدة متسقة.
