
# تدقيق جهاز DINSTAR من لوحة الويب

## نتيجة الوصول

تم الدخول إلى لوحة الويب الداخلية بنجاح عبر `https://192.168.11.2/enFrame.htm` بعد تأكيد المستخدم. عنوان اللوحة الظاهر هو **UC2000-VE Business**. لم يتم حفظ أي إعداد أو إرسال SMS أو تنفيذ مكالمة.

## الأقسام الظاهرة في القائمة

| القسم الظاهر | الغرض المتوقع |
|---|---|
| Information & Statistics | معلومات الجهاز والإحصاءات والحالة |
| Quick Setup Wizard | إعداد أولي سريع؛ لا يُستخدم أثناء التدقيق القراءة فقط |
| Network Configuration | عنوان IP وDNS والبوابات والبروتوكولات |
| Mobile Configuration | الشرائح/القنوات الخلوية وحالة التسجيل ومعلومات المشغل |
| SMS and USSD | إرسال/استقبال SMS وطلبات USSD |
| Call Configuration | SIP/PSTN ومسارات المكالمات والقواعد |
| Advanced | إعدادات متقدمة وخدمات وبروتوكولات |
| Diagnostic | اختبارات الاتصال والسجلات والتشخيص |
| Tools | أدوات النظام والنسخ والتحديث وإدارة الإعدادات |

الخطوة التالية هي فتح صفحات Information & Statistics وMobile Configuration وSMS and USSD وCall Configuration للقراءة فقط، واستخراج الطراز التفصيلي والإصدار وعدد القنوات وحالة الشرائح وواجهات التكامل، ثم مطابقة ذلك مع خدمات RED الموجودة في `backend-server`.

## خريطة المعلومات التفصيلية

تحت قسم Information & Statistics ظهرت صفحات System Information وMobile Information وSIP Information وTCP/UDP وRTP وسجل مكالمات SIP وسجل IP-to-GSM وتقرير CDR وتقرير Lock BCCH وحالة المكالمات الحالية وأحداث GSM. هذا يؤكد أن الجهاز يجمع بين بوابة GSM متعددة القنوات وواجهة SIP/RTP، مع تقارير مكالمات وسجلات خلوية قابلة للمراجعة.

## معلومات النظام المقروءة

صفحة System Information أكدت أن الجهاز هو **UC2000-VE Business**، وأنه يعمل بإصدار Package/Software/Web موحد من السلسلة `04240302` بتاريخ أغسطس 2025، مع Hardware PCB 27 وBoot Version 2 وKernel Version 2 وDSP ARM_32 وUserboard B4.11.19.14L2. الشبكة ثابتة على العنوان الداخلي الذي زوّده المستخدم، وDNS مضبوط على خادم عام مع خانة احتياطية فارغة. الترخيص الظاهر Basic Function، وعدد المنافذ الصالحة الظاهر 8، وحالة التسجيل السحابي Not Registered.

تمت قراءة الصفحة فقط. لم يتم الضغط على Refresh أو Enable أو أي عنصر حفظ، ولم تُنسخ معرّفات الجهاز الحساسة إلى المحادثة.

## نتائج البحث الخارجي

المصدر الرسمي يصف UC2000-VE بأنه بوابة GSM/WCDMA/LTE ذات 4 أو 8 قنوات، تدعم الصوت وSMS وSIP وRTP وHTTP API وSMPP، مع إدارة Web ونسخ احتياطي واستعادة وCDR وحدود دقائق ومراقبة المكالمات.[1] دليل HTTP API الرسمي يعرّف إرسال واستقبال SMS، الاستعلام عن حالة الإرسال والتسليم، قراءة معلومات المنافذ، CDR، حالة الجهاز، وPush Events إلى خادم العميل.[2] كما توضح صفحة الشركة أن SMSBox مثال برمجي للربط عبر HTTP API.[3]

الـ Push Events الرسمية تشمل الرسائل الواردة، نتائج الإرسال، حالة التسليم، USSD، حالة تسجيل الشرائح، CDR، وحالة الجهاز. هذا مناسب لتصميم خدمة RED تعمل كوسيط آمن: تستقبل الأحداث من البوابة، تتحقق من المصدر، تحفظ أقل قدر لازم من البيانات، ثم تعرضها للمستخدمين المصرّح لهم. لا ينبغي أن يتصل تطبيق الهاتف مباشرة ببوابة DINSTAR أو يحمل بيانات اعتمادها.

## المطابقة مع مشروع RED

خدمة `DinstarHardwareService` في RED تستخدم المصادقة Digest وBasic معاً، وتتحقق من العنوان الخاص، وتدعم `send_sms` ونتائج الإرسال والتسليم والرسائل الواردة وUSSD وCDR وحالة المنافذ. كما أن مسار المكالمات مصمم للمرور عبر Asterisk/PJSIP بدلاً من اختراع endpoint للاتصال داخل البوابة.

تم اكتشاف وإصلاح خلل في `admin_dashboard/src/pages/DinstarControl.tsx`: الواجهة كانت ترسل قيم الترميز السلكية `unicode` و`gsm-7bit` إلى Backend، بينما عقد Backend يتوقع القيم الداخلية `UCS2` و`GSM7BIT` ثم يحولها إلى صيغة البوابة. بعد الإصلاح أصبحت القيم متطابقة مع العقد، ونجحت فحوص TypeScript وعقد API وحراس الواجهة وبناء لوحة الإدارة.

محاولة فتح `/api/get_port_info` مباشرة من المتصفح أعادت Forbidden؛ وهذا متوقع لأن HTTP API في UC2000-VE يتطلب مصادقة HTTP API وليس مجرد تصفح صفحة الويب. لذلك يجب أن يبقى الاتصال من Backend عبر عميل OkHttp المجهز بالمصادقة، لا من تطبيق الهاتف أو المتصفح مباشرة.

## مفاتيح الربط المطلوبة في Backend

الكود الحالي يدعم الإعدادات التالية: `red.dinstar.enabled` و`red.dinstar.ip` و`red.dinstar.port` و`red.dinstar.scheme` و`red.dinstar.username` و`red.dinstar.password`، إضافة إلى مهلات الاتصال والاستطلاع واكتشاف الشبكة. يجب ضبط العنوان على الجهاز المكتشف، والمنفذ/المخطط وفق واجهة UC2000-VE الفعلية، ووضع كلمة المرور في مدير أسرار أو متغير بيئة لا في Git.

بما أن الجهاز يعمل الآن على HTTPS بعنوان داخلي ويظهر 8 منافذ صالحة، فالإعداد المرشح هو HTTPS على المنفذ المستخدم فعلياً من لوحة الويب، مع اختبار `discoverGateway` وقراءة المنافذ قبل السماح بعمليات SMS أو مكالمات. لا توجد حاجة لتفعيل subnet discovery الواسع؛ الأفضل تسجيل العنوان المعروف فقط لتقليل خطر SSRF أو ضم جهاز غير مقصود.

## حالة الدخول الحالية

عند إعادة فتح صفحة الإدارة ظهر تحذير الجهاز: `Your IP login failed too many times, forbid to try again!`. لن أكرر محاولات تسجيل الدخول ولن أجرّب كلمات مرور أو طرق تجاوز؛ ذلك قد يطيل الحظر. الوصول السابق نجح وأثبت الطراز، لكن الجولة الحالية تحتاج انتهاء مهلة الحظر أو رفعه من مسؤول الجهاز/الانتظار ثم تسجيل دخول واحد صحيح.

هذا الحظر منفصل عن مشكلة وصول Backend: الجهاز متاح من متصفح المستخدم على الشبكة المحلية، بينما بيئة الخادم السابقة انتهت بمهلة عند محاولة الوصول إلى العنوان الداخلي. يلزم تشغيل Backend في نفس الشبكة أو عبر VPN/وكيل آمن قبل اختبار HTTP API من التطبيق.

## استئناف الفحص بعد رفع الحظر

بعد تغيير عنوان IP ورفع الحظر، عادت جلسة لوحة UC2000-VE Business إلى صفحة الإطار الرئيسية، وأصبحت قائمة الجهاز متاحة من جديد. الأقسام المطلوب فحصها بالترتيب هي Information & Statistics، Mobile Configuration، SMS and USSD، ثم Call Configuration. سيبقى الفحص قراءة فقط.

## صفحات الحالة المكتشفة بعد استئناف الجلسة

تم فتح قائمة Information & Statistics، وتبيّن أن Mobile Information تُحمّل من الصفحة `enSysInfo_Mobile.htm`. هذه الصفحة هي المصدر التالي لحالة كل قناة وSIM والإشارة والمشغل، ويجب قراءتها قبل اختيار منفذ SMS أو مسار المكالمات.

## حالة المنافذ والشرائح

صفحة Mobile Information أظهرت 8 منافذ GSM (0 إلى 7). المنافذ 0 و1 و3 و4 و5 و6 و7 تظهر `No SIM Card`، بينما المنفذ 2 فقط يظهر `Mobile Registered` مع حالة المكالمة `Idle` وحد المكالمة `Normal`. هذا يعني أن اختيار المنفذ الصحيح الحالي للقراءة/الاختبار هو **port 2**، ولا يجوز افتراض أن بقية المنافذ جاهزة لـSMS أو المكالمات.

محاولة فتح صفحة SIP Information عبر اسم ملف مخمّن أعادت `Site or Page Not Found`، لذلك لن أخمّن رابطها أو أغيّر أي إعداد؛ سأستخرج الرابط من HTML قائمة الجهاز أو أعود إلى القائمة لاكتشافه بدقة.

## رابط SIP الصحيح

من DOM قائمة الجهاز ظهر أن صفحة SIP Information الصحيحة هي `enSysInfo_SIP.htm`، وليس الاسم الذي جُرّب سابقاً. ستُقرأ هذه الصفحة مباشرة في الخطوة التالية.

## أقسام SMS وUSSD في الجهاز

قائمة UC2000-VE تعرض أقساماً منفصلة لـ SMS Send Overview وSMS Send Limit Settings وSMS Routing وSMSC Switch Setting وSend SMS وSMS Outbox وSMS Inbox وUSSD وSMS Settings. هذا يطابق قدرات HTTP API الرسمية ويشير إلى أن اختيار المنفذ وسياسة الحد والتوجيه يجب أن تُقرأ قبل إرسال أي رسالة. لم يتم فتح Send SMS أو الضغط على أي زر إرسال.

## حالة صندوق SMS

صفحة `enSmsRecvNew.htm` فتحت بنجاح، وتعرض فلاتر التاريخ والمنفذ والرقم وIMSI والتصدير والتحديث والمسح. النتيجة الحالية هي **0 رسائل واردة**. لم أضغط Refresh أو Clear أو Save، ولم يتم إرسال أو حذف أي رسالة.

## أقسام المكالمات في الجهاز

قسم Call Configuration يعرض SIP Configuration وSIP Trunk Configuration وSIP Trunk Group Configuration وPort Configuration وPort Group Configuration وDigit Map وIP->Tel Routing وTel->IP Routing وTel->IP Caller Manipulation وService Parameter وMedia Parameter. هذا يطابق تصميم RED الذي يمرر الصوت عبر Asterisk/PJSIP، ويعني أن جاهزية المكالمات تعتمد على تسجيل SIP ومسارات IP↔Tel معاً، وليس على endpoint HTTP بسيط للاتصال.

## ملاحظة الإطارات في لوحة الجهاز

صفحات الإعدادات الفرعية تُفتح داخل `mainframe` مع بقاء عنوان `enMenu.htm#` في المتصفح، لذلك قد لا يظهر الانتقال في عنوان الصفحة. صفحة SIP Information نجحت عند فتحها مباشرة، أما صفحات Call Configuration فتحتاج استخراج `href` من HTML القائمة بدلاً من التخمين أو تكرار النقر.

## إعدادات Port Configuration المقروءة

صفحة `enPortList.htm` تُظهر أن المنافذ 0 إلى 7 مفعّلة، ولكل منفذ SIP User ID وAuthenticate ID متسلسلان، ومنافذ SIP محلية 5060 إلى 5067. حقل Register to متاح بخيارات No Register وSIP Proxy و`sip-trunk-0 <Asterisk-Peer>`. القيم المعروضة تشير إلى أن الحسابات غير المسجلة سابقاً مرتبطة بتكوين Asterisk-Peer، لكن صفحة SIP Information ما زالت تعرض جميع الحالات Unregistered؛ لذلك مسار المكالمات غير جاهز بعد حتى يتم تسجيل Asterisk/PJSIP في نفس الـ trunk.

المنفذ 2 فقط هو الذي لديه SIM مسجلة، وتظهر له قيمة PSTN Hotline في الصفحة؛ لم أعدّلها ولم أضغط Save. بما أن الصفحة تعرض حقول كلمات مرور، لم تُنسخ أي كلمة مرور إلى التقرير أو المحادثة.

## SIP Trunk الفعلي وعدم التطابق

صفحة `enIpCfg.htm?run` تعرض SIP Trunk واحداً باسم `Asterisk-Peer` وعنوان `192.168.11.104` ومنفذ UDP `5060` وKeepAlive مفعّلاً. في المقابل، صفحة SIP Information تعرض كل المنافذ 0–7 وPort Group 0 بحالة `Unregistered`. لذلك لا يمكن إعلان جاهزية المكالمات؛ المسار موجود في الجهاز لكنه غير مسجل من جهة Asterisk.

توجد في مستندات المشروع القديمة عناوين افتراضية مثل `192.168.11.1` و`192.168.11.2`، بينما جهاز المستخدم ظهر الآن على `192.168.11.2` وTrunk يشير إلى `192.168.11.104`. يجب اعتماد عنوان Asterisk الفعلي من الشبكة الحالية قبل تعديل البوابة، ثم تشغيل Asterisk/PJSIP على UDP 5060، تعريف النظير للحسابات 0–7، والتحقق من التسجيل. لن أغيّر عنوان Trunk أو الحسابات عبر لوحة الجهاز من دون تأكيد لأن ذلك قد يقطع المكالمات.

## صحة Backend المحلي

من متصفح المستخدم المحلي، أعاد `http://127.0.0.1:8088/health` حالة `UP`، وكانت PostgreSQL وMongoDB وRedis وMinIO كلها `UP`. هذا يؤكد أن خدمات RED الأساسية تعمل على الجهاز المضيف. الخطوة المتبقية هي فحص binding الخاص بـ DINSTAR من Backend نفسه، ثم اختبار قراءة port 2 عبر مسار الإدارة، لا إرسال SMS أو مكالمة.

## اختبار مسار التطبيق

نقطة صحة Backend المحلية تعمل وتعيد حالة الخدمات الأساسية `UP`. أما `GET /api/admin/dinstar/fleet/ports` فأعاد `AUTHENTICATION_REQUIRED`، وهو سلوك صحيح للحماية لكنه يعني أن جلسة متصفح الجهاز لا تمنح تلقائياً جلسة Backend. يجب تسجيل دخول RED/لوحة الإدارة أولاً ثم إعادة طلب قائمة المنافذ من مسار مصادق عليه؛ لا ينبغي تعطيل الحماية أو استدعاء endpoint من تطبيق الهاتف بلا تذكرة جلسة.

## لوحة RED بعد تسجيل الدخول

نجح تسجيل الدخول إلى YOUNES Master Admin عبر متصفح المستخدم. صفحة إدارة خدمة PSTN تعرض 18 مستخدماً، منهم 17 مفعّلاً لهم PSTN، مع حدود يومية واستهلاك مسجل؛ كما يظهر مسؤول RED بحد يومي 100 واستهلاك 5. هذا يؤكد أن صلاحيات PSTN موجودة في التطبيق ومفصولة عن صلاحيات بوابة DINSTAR، ولا يعني وحده أن SIP أو البوابة متصلان.

## جرد المنصة من داخل التطبيق

بعد تسجيل الدخول إلى لوحة RED وفتح جرد بيانات المنصة، ظهر: بوابة واحدة، و8 لقطات منافذ، و24 في سجل المكالمات، و0 مكالمات نشطة، و0 سجلات PSTN. هذا يعني أن التطبيق يرى سجل البوابة/المنافذ على مستوى البيانات، لكنه لا يثبت نجاح مكالمة PSTN حقيقية. كما يظهر وجود 9 رسائل مشفرة كعدد فقط، مع عدم عرض محتوى الرسائل أو الأسرار.

## نتائج الرسائل والمكالمات من التطبيق

مركز الرسائل في لوحة RED يعمل على مسار إحصاءات حي لكنه يعرض شرطات للرسائل اليومية ومعدل التوصيل والطابور، ولا يعرض محتوى الرسائل أو هوية المرسل. سجل المكالمات يعرض 24 مكالمة، منها 2 تم الرد عليها و22 فائتة/مرفوضة. مكالمات PSTN_DINSTAR الظاهرة في السجل الأخيرة حالتها فائتة أو منتهية ومدة المكالمة فارغة، وهذا يتوافق مع حالة UC2000-VE التي أظهرت SIP Unregistered. التطبيق يسجل الأحداث ويعرضها، لكن مسار PSTN التشغيلي غير سليم بعد.

## تحديثات الربط البرمجية

تم تحديث defaults التشغيلية في `docker-compose.yml` و`docker-compose.lan.yml` و`enable-dinstar-ready.ps1` و`configure-windows-lan.ps1` من عنوان المصنع القديم `192.168.11.1` إلى عنوان UC2000-VE المكتشف `192.168.11.2`. متغير `DINSTAR_IP` ما زال أعلى أولوية، لذلك يمكن تغيير العنوان دون تعديل الكود. قواعد SIP/RTP في Windows أصبحت محصورة على عنوان البوابة الجديد.

لم أغيّر `SIP Trunk` داخل الجهاز؛ فهو يشير إلى `192.168.11.104:5060`، وهو عنوان Asterisk/Windows المضيف المتوقع من سكربت التشغيل. قبل تشغيل المكالمات يجب التأكد من أن عنوان Windows الحالي هو فعلاً `192.168.11.104` وأن Asterisk يستمع على UDP 5060، ثم إعادة فحص SIP Information حتى تصبح القنوات Registered.

## حماية endpoints داخل لوحة RED

محاولة فتح `/api/master/v1/stats/realtime` مباشرة أعادت `AUTHENTICATION_REQUIRED`، مثل endpoint منافذ DINSTAR. هذا لا يعني تعطل مركز الرسائل؛ صفحة المركز نفسها فتحت بعد تسجيل الدخول، لكن المتصفح المباشر لا يرسل ترويسة JWT التي يضيفها عميل اللوحة. الحماية تعمل كما هو متوقع، ولا ينبغي تخفيفها أو وضع JWT في رابط URL.

## إعادة التحقق الشامل

أعاد Backend المحلي حالة `UP` مع PostgreSQL وMongoDB وRedis وMinIO. بعد فتح لوحة RED المصادق عليها، ظهرت صحة النظام لكل من PSTN_GATEWAY وBACKEND وبقية الخدمات، مع حالة تشغيلية مباشرة. هذا يثبت صحة طبقة الخدمات، لكنه لا يتجاوز حقيقة أن SIP في UC2000-VE غير مسجل؛ لذلك لا تزال جاهزية المكالمات الخارجية بحاجة إلى فحص Asterisk/PJSIP على المضيف.

## تشخيص الوصول إلى Asterisk من البوابة

أعيد تسجيل الدخول إلى UC2000-VE وفحص Mobile Information: المنفذ 2 ما زال الوحيد بحالة `Mobile Registered` وباقي المنافذ بلا SIM. تؤكد SIP Information أن المنفذ 2 وبقية المنافذ ما زالت `Unregistered`، بينما يبقى SIP Trunk مضبوطاً على `192.168.11.104:5060/UDP` مع KeepAlive مفعّل.

تم تشغيل Ping تشخيصي غير هدّام من UC2000-VE إلى `192.168.11.104` بأربع رزم، وكانت النتيجة `Sent = 4, Received = 0, Lost = 4 (100% loss)`. هذا يثبت أن البوابة لا تصل حالياً إلى عنوان Asterisk المضبوط، وهو سبب شبكي سابق على تسجيل SIP. يجب فحص عنوان واجهة Windows/الـNIC، والتوجيه بين Docker/WSL والشبكة `192.168.11.0/24`، وقواعد ICMP/SIP/RTP قبل تعديل حسابات البوابة أو تجربة مكالمة.

كما أن محاولة قراءة `/health` عبر `http://192.168.11.104:8088/health` من المتصفح المحلي انتهت بمهلة اتصال. لا يثبت ذلك وحده حالة UDP 5060، لكنه يدعم أن عنوان `192.168.11.104` ليس حالياً مضيف RED متاحاً عبر الشبكة. لذلك يجب عدم تغيير بيانات حسابات SIP أو تجربة مكالمة؛ المطلوب أولاً تحديد عنوان واجهة Windows الفعلي وتشغيل طبقة Compose LAN عليه.

## فحص الشبكة والنقل

صفحة Local Network تؤكد أن UC2000-VE يعمل بعنوان ثابت `192.168.11.2/24` مع بوابة افتراضية `192.168.11.1` وDNS أساسي `8.8.8.8`. اختبار Ping قصير إلى البوابة الافتراضية نفسها انتهى أيضاً بنسبة فقدان `100%` (4 من 4)، كما سبق أن فشل الاختبار إلى `192.168.11.104`. قد يمنع المضيفان ICMP، لكن النتيجتين مع مهلة HTTP إلى `.104` تجعلان العنوان المضبوط في SIP Trunk غير قابل للتحقق على أنه مسار Asterisk صالح.

تظهر إحصاءات TCP/UDP أن للجهاز حركة متراكمة عامة، لكن صفحة RTP لا تعرض أي جلسة وسائط أو Peer IP أو حزم RTP حالية. لا توجد إذاً مكالمة صوتية نشطة، ولا ينبغي إجراء اختبار اتصال قبل إصلاح طبقة الشبكة وظهور تسجيل SIP للمنفذ 2.

## قواعد وصول UC2000-VE

صفحة Access Rules لا تعرض أي قاعدة مفعّلة أو صف تحكم يقيّد عنواناً أو بروتوكولاً أو منفذاً. لذلك لا يظهر من لوحة الجهاز أن جدار الوصول الداخلي يمنع `192.168.11.104` أو UDP 5060. يبقى التركيز على المضيف المحلي الذي يفترض أن يشغّل Asterisk، وواجهة الشبكة السلكية، وDocker/WSL، وقواعد جدار حماية Windows.

## فحص Windows محلي آمن

أضيف السكربت `scripts/verify-dinstar-lan.ps1` كفحص قراءة فقط على جهاز Windows المحلي. يفحص وجود عنوان إدارة في الشبكة `192.168.11.0/24`، وإتاحة HTTPS للبوابة، واستماع UDP 5060، وقواعد جدار YOUNES الخاصة بالبوابة، وحالة حاويتي `red-pstn-gateway` و`red-backend`. لا يغير إعدادات الشبكة، ولا يعيد تشغيل Docker، ولا يرسل SMS، ولا ينشئ مكالمة. يجب أن يجتاز هذا الفحص قبل تغيير SIP Server داخل UC2000-VE أو اختبار PSTN فعلي.

## تعريف البوابة الافتراضية

تم فتح `http://192.168.11.1/` من متصفح المستخدم المحلي، وظهرت صفحة تسجيل دخول **4G CPE Yemen**. إذن العنوان `192.168.11.1` هو جهاز CPE/راوتر مستقل يعمل كبوابة افتراضية للـUC2000-VE، وليس عنوان Asterisk ولا بوابة DINSTAR ثانية. فشل Ping من UC2000-VE إلى هذا العنوان لا يعني غياب جهاز CPE بالضرورة، لأن الجهاز قد يمنع ICMP؛ لكنه لا يفسر مهلة HTTP إلى `192.168.11.104`، والتي تبقى دليل المشكلة الأهم في مسار Asterisk.

## عنوان مضيف Asterisk الصحيح

أظهرت إعدادات شبكة Windows أن واجهة **Realtek Gaming 2.5GbE** المتصلة بشبكة الإدارة تعمل بعنوان ثابت `192.168.11.105/24` وسرعة ربط 1 Gbps. لذلك العنوان `192.168.11.104` الموجود في SIP Trunk للـUC2000-VE عنوان قديم أو غير مستخدم، وهو يفسر فقدان Ping ومهلة HTTP وحالة `Unregistered` لكل منافذ SIP. عنوان SIP Server الصحيح الذي يجب مراجعته قبل حفظ التغيير هو `192.168.11.105` مع UDP 5060؛ لا تزال عملية الحفظ داخل الجهاز مؤجلة حتى التحقق من استماع Asterisk على هذا العنوان.

## تعارض إعداد SIP Proxy العام

قراءة صفحة `enSIPCfg.htm` أظهرت أن **SIP Proxy العام** مضبوط على `192.168.11.131:8088`، مع نقل UDP وفترة تسجيل 1800 ثانية، بينما SIP Trunk السابق مضبوط على `192.168.11.104:5060`. هذا يعني أن البوابة تحتوي على مسارين قديمين مختلفين، ولا يصح افتراض أن تغيير SIP Trunk وحده سيعيد التسجيل. قبل الحفظ يجب تحديد قيمة `Register to` الفعلية للمنفذ 2: إن كان يستخدم SIP Proxy فالعنوان والمنفذ المطلوبان هما Asterisk على `192.168.11.105:5060`؛ وإن كان يستخدم SIP Trunk 0 فيجب تصحيح هذا الـTrunk فقط. لا يتم حفظ أي من القيم قبل تأكيد أثرها التشغيلي.

## مسار المنفذ 2 المثبت

أظهرت صفحة `enPortList.htm` أن المنفذ 2 يختار فعلياً `sip-trunk-0 <Asterisk-Peer>` ضمن حقل `Register to`، ويستخدم SIP User ID وAuthenticate ID بقيمة `2` ومنفذ SIP محلي `5062`. لذلك **لن يتم تغيير SIP Proxy العام** `192.168.11.131:8088` في هذه المرحلة. التغيير المحدد الوحيد المقترح هو تعديل عنوان `Asterisk-Peer` داخل SIP Trunk 0 من `192.168.11.104` إلى عنوان مضيف Asterisk الفعلي `192.168.11.105`، مع إبقاء UDP 5060 والوصف وKeepAlive كما هي.

## نجاح تسجيل SIP

بعد تأكيد المستخدم، تم تعديل **SIP Trunk 0 / Asterisk-Peer** فقط من `192.168.11.104` إلى `192.168.11.105` مع إبقاء UDP `5060` والوصف وKeepAlive مفعلة. أعاد الجهاز إلى صفحة الـTrunk بالقيمة الجديدة، ثم أظهرت `enSysInfo_SIP.htm` أن المنافذ 0–7 أصبحت جميعاً `Registered`، ومن ضمنها **المنفذ 2** الذي يحتوي على SIM المسجلة. لم يتم تغيير SIP Proxy العام أو حسابات SIP أو منافذ الجهاز، ولم يُرسل SMS ولم تُجرَ مكالمة.

تظهر `Port Group 0` بحالة `Unregistered` رغم تسجيل كل حساب منفرد؛ هذه مجموعة مستقلة عن تسجيل حسابات المنافذ ولا تمنع استخدام المنفذ 2 عبر Asterisk-Peer. ستبقى تحت المراقبة ولا تحتاج إلى تعديل ما لم يكن تصميم التوجيه في Asterisk يعتمد عليها صراحةً.

## تحقق SMS بالقراءة فقط

بعد نجاح SIP، فتحت صفحة SMS Inbox للقراءة فقط. تؤكد الصفحة وجود رسالتين واردتين حديثتين عبر **المنفذ 2**، وهو دليل تشغيلي على أن الشريحة والتسجيل الخلوي والاستقبال يعملون. لم تُعرض أرقام المرسلين أو IMSI أو محتوى الرسائل في التقرير، ولم يُستخدم Refresh أو Export أو Clear، ولم تُنشأ رسالة صادرة. ما زال إرسال SMS مؤجلاً إلى تأكيد منفصل مع رقم اختبار ونص اختبار يحدده المستخدم.
