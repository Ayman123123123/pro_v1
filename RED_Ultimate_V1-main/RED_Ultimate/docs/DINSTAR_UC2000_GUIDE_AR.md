# بوابات DINSTAR UC2000-VE — دليل التشغيل والربط

دليل عملي لربط أجهزة **UC2000-VE-8G** و**UC2000-VE-8T** بمشروع RED،
وتشغيل عدة أجهزة معًا، والتعرّف عليها تلقائيًا.

كل ما هنا مستمد من ورقة بيانات المُصنّع الرسمية ومن معايير 3GPP وRFC
المذكورة في مواضعها. ما لا يوجد له مصدر موثق مُعلَّم صراحةً بأنه غير
مدعوم بدل تلفيق سلوك.

---

## 1. الجهازان — الحقائق

| | **UC2000-VE-8G** | **UC2000-VE-8T** |
|---|---|---|
| القنوات | 8 | 8 |
| شقوق SIM | 8 قابلة للتبديل الساخن | 8 قابلة للتبديل الساخن |
| الشبكة | GSM 850/900/1800/1900 MHz | LTE-FDD / LTE-TDD / WCDMA / GSM |
| VoLTE | ✗ | ✓ |
| الترميزات | G.711A/U · G.723.1 · G.729A/B | + G.722 · AMR |
| SIP | v2.0 (RFC3261) عبر UDP/TCP/TLS | نفسه |
| الوسائط | RTP / SRTP | نفسه |
| DTMF | RFC2833 · SIP Info | نفسه |
| الشبكة السلكية | 2× 10/100/1000 Base-T RJ45 | نفسه |
| الأبعاد | 250 × 156 × 32.5 مم · 1.07 كجم | نفسه |
| الطاقة | 100‑240V @ DC12V · أقل من 25 واط | نفسه |
| واجهة البرمجة | HTTP API للرسائل وحالة المنافذ | نفسه |

**النطاقات الترددية للطراز ‑8T لا تُستنتج من اسم الطراز.** تعتمد على
متغيّر الراديو المركّب (Type A / E / V / J / AU) وتُقرأ من ملصق الجهاز.
لذلك يسجّلها المشروع كنص وصفي ولا يبني عليها منطق توجيه.

**المتغيّران الرباعيان** ‑4G و‑4T من العائلة نفسها بأربع قنوات، وهما
مدعومان في `DinstarModelProfile` لأن تثبيت العدد على 8 كان يجعل الخادم
يستعلم عن منافذ غير موجودة.

## 2. مسار الصوت — لماذا لا نتصل من البوابة مباشرة

```
تطبيق RED ──WebRTC──► الخادم ──AMI──► Asterisk ──PJSIP/SIP──► DINSTAR ──GSM──► المستقبِل
```

لا يوجد في واجهة UC2000 أي endpoint موثق لإجراء مكالمة. الاتصال يتم
حصرًا عبر SIP، وAsterisk هو من يتحدث SIP. لذلك:

- `DinstarHardwareService.initiateCall()` تُرجع **501 Not Implemented**
  عمدًا، و`POST /api/admin/dinstar/dial` تُرجع **410 Gone**.
- الخادم هو الوحيد المخوَّل بإطلاق مكالمة، بعد التحقق من اعتماد الحساب
  وتفعيل PSTN والحد اليومي.
- السياق `from-red-client` في `extensions.conf` يُنهي أي محاولة من
  عميل SIP للاتصال بالبوابة مباشرة — وإلا لالتُفَّ على هذه القيود.

## 3. واجهة HTTP — العمليات الموثقة فقط

**المصادقة: HTTP Digest** (وBasic على الإصدارات الأقدم). يسجّل
`DinstarConnectionFactory` المُصادِقَين معًا ويختار حسب ترويسة
`WWW-Authenticate`، ويخزّن النتيجة مؤقتًا لتفادي جولة تحدٍّ مع كل طلب.

| العملية | الطريقة والمسار |
|---|---|
| حالة المنافذ | `GET /api/get_port_info` |
| حالة الجهاز | `POST /api/get_status` |
| إرسال SMS | `POST /api/send_sms` |
| نتيجة الإرسال | `POST /api/query_sms_result` |
| حالة التسليم | `POST /api/query_sms_deliver_status` |
| الرسائل الواردة | `GET /api/query_incoming_sms` |
| إرسال USSD | `POST /api/send_ussd` |
| رد USSD | `GET /api/query_ussd_reply` |
| سجل المكالمات | `POST /api/get_cdr` |
| إعادة تشغيل وحدة | `GET /api/set_port_info?action=reset` |
| تحويل المكالمات | `GET /api/set_port_info?action=CallForward` |
| تشغيل/إطفاء منفذ | `GET /api/set_port_info?action=power` |

**غير مدعوم عمدًا:** إعادة تشغيل الجهاز كاملًا، تعديل إعدادات SIP،
ترقية البرنامج الثابت، إعادة ضبط المصنع. تُنفَّذ من واجهة الجهاز
الأصلية بعد التأكد من عدم وجود مكالمات نشطة.

### رموز الاستجابة — عطل كان يقلب النجاح فشلًا

التوثيق الرسمي (§2.3 و§7.3) يميّز رمزين للقبول:

| الرمز | المعنى | العمليات |
|---|---|---|
| **200** | طُلب ونُفِّذ | الاستعلامات والأوامر المتزامنة |
| **202** | **قُبل وسيُنفَّذ لاحقًا** | `send_sms`، `send_ussd` |
| 400 | صيغة الطلب غير صالحة | — |
| 413 | المستلمون أو النص يتجاوز الحد | — |
| 486 | المنفذ مشغول | USSD |
| 500 | خطأ داخلي | — |
| 503 | المنفذ غير مسجّل | USSD |
| 550 | لا يوجد منفذ متاح للإرسال | SMS |

كان الفحص `error_code == 200` فقط. الإرسال وUSSD **غير متزامنَين
بطبيعتهما** (الرسالة تدخل طابورًا) فيردّان `202`، فكان كل أمر ناجح
يُرمى استثناءً ويُسجَّل فشلًا **رغم تنفيذه فعلًا على الشبكة**. المسؤول
يرى «فشل» فيعيد المحاولة، فتُرسل الرسالة مرتين.

### حدود الإرسال — رقمان مختلطان

| الحد | القيمة الصحيحة | ما كان في الشيفرة |
|---|---|---|
| المستلمون في `send_sms` | **128** | 32 ❌ |
| حجم نص الطلب | **1500 بايت** | بلا فحص ❌ |
| المستلمون في `query_sms_result` | 32 | — |

الرقم 32 يخص **استعلام النتائج** لا الإرسال، فكان الحد الأضيق يرفض
دفعات مشروعة قبل أن تصل للبوابة. والحجم يُقاس **بالبايت**: 800 حرف
عربي = 1600 بايت وتتجاوز الحد رغم أنها أقل من 1500 «حرف».

### الترميز — قيمة كانت تُرسَل بصيغة لا تفهمها البوابة

البوابة تتوقع `'gsm-7bit'` أو `'unicode'` (§2.2)، والشيفرة كانت ترسل
`"GSM7BIT"`. القيمة غير المعروفة تعني رجوع البوابة إلى الافتراضي
`unicode`، فرسالة ASCII تُرسَل UCS2: **السعة تهبط من 160 حرفًا إلى 70**
وتتضاعف الأجزاء والتكلفة. الترجمة الآن في `wireEncoding()`.

### شهادة TLS

تُصدِر البوابة شهادة موقّعة ذاتيًا باسم لا يطابق عنوان IP. يقبلها
المشروع **بشرطين معًا**: أن يكون العنوان خاصًا (RFC 1918)، وأن يكون على
شبكة إدارة معزولة. أي عنوان عام يُرفض عند التسجيل بـ
`PRIVATE_ADDRESS_REQUIRED` — لأن الثقة العمياء بشهادة على الإنترنت
العام تعني إمكانية اعتراض المكالمات.

## 4. قراءة الإشارة — عطل جوهري أُصلح

### ما كان يحدث

`get_port_info` يُعيد حقل `signal` كما تُرجعه وحدة الراديو عبر `AT+CSQ`،
وهو مُعرَّف في **3GPP TS 27.007 §8.5**:

| القيمة الخام | المعنى |
|---|---|
| 0 | ‎-113 dBm أو أقل |
| 1 | ‎-111 dBm |
| 2..30 | ‎-109 .. ‎-53 dBm (خطوة 2 dBm) |
| 31 | ‎-51 dBm أو أعلى |
| **99** | **غير معروفة أو غير قابلة للكشف** |
| 100..191 | RSCP ممتد لـ TD-SCDMA |

كانت الشيفرة تحسب:

```kotlin
val signalRaw = raw["signal"]?.toInt()?.coerceIn(0, 31) ?: 0
"signal" to (signalRaw / 31.0 * 100).roundToInt()
```

القيمة **99 تعني «لا توجد شبكة»**، لكن `coerceIn(0, 31)` كانت تحوّلها
إلى 31 أي **100%**. فكانت شريحة بلا أي تغطية تظهر في اللوحة بإشارة
كاملة. والأسوأ: `DinstarLoadBalancer` يرتّب المنافذ بالإشارة تنازليًا،
فكان **يختار الشريحة الميتة أولًا لكل مكالمة صادرة**. المستخدم يرى
«فشل الاتصال» والمسؤول يرى إشارة ممتازة.

### الإصلاح

`DinstarSignal.kt` يفسّر القراءة حسب المعيار ويعيد `null` صراحةً عند
تعذّر القياس بدل تلفيق رقم:

```
dBm = 2 × raw − 113          للمدى 0..31
dBm = raw − 216              للمدى الممتد 100..191
99 و199                       ⇒ لا قياس (null)
```

ويضيف `signalUsable`: الحد العملي **‎-100 dBm** (قراءة خام 7). تحته
تكون المكالمة عرضة للانقطاع، فلا يختار الموزّع المنفذ.

**النتيجة في اللوحة:** «14 شريحة مسجّلة، منها 10 جاهزة». هذا الفارق
كان مخفيًا تمامًا.

## 5. تشغيل عدة أجهزة

### السجل

جدول `telecom_gateways` كان يقبل عدة صفوف منذ V12، لكن الشيفرة كانت
تخاطب `red.dinstar.ip` وحده. هجرة **V23** أضافت ما يلزم لأسطول حقيقي:
`port_count` و`routing_priority` و`health_state` و`pjsip_endpoint`
و`serial_number`.

### هوية الجهاز

**العنوان الشبكي ليس هوية.** مع DHCP قد يتبدّل العنوان فتتضاعف
السجلات. لذلك يُشتق معرّف البوابة من **الرقم التسلسلي** حين تُفصح عنه
`get_status`، ويُستخدم `host:port` بديلًا عند غيابه.

### التوجيه

`DinstarLoadBalancer.selectPort(number)` يمسح الأسطول كله ويستبعد:

1. المنافذ غير المسجّلة على الشبكة.
2. المنافذ المشغولة (`ACTIVE` / `DIALING`).
3. **المنافذ بلا إشارة صالحة** — الشرط الذي كان مفقودًا.

ثم يرجّح الباقي:

| العامل | الوزن | السبب |
|---|---|---|
| قوة الإشارة | 1.0 × النسبة | جودة المكالمة |
| مطابقة المشغل | 35 | مكالمة داخل الشبكة أرخص |
| الاستخدام السابق | ‎-5 لكل مكالمة | يمنع حظر الشريحة |
| الدور (round-robin) | 8 | عدالة التوزيع |
| أولوية البوابة | ‎-0.5 × الأولوية | تفضيل جهاز على آخر |

إن لم يوجد أي منفذ صالح تُعاد `null` وتفشل المكالمة برسالة واضحة —
أصدق من محاولة اتصال على منفذ ميت.

### مطابقة المشغل

| البادئة | المشغل | محمول؟ |
|---|---|---|
| 70 | واي (كانت HiTel) | ✓ |
| 71 | سبأفون | ✓ |
| 73 | يو (كانت MTN حتى 2021) | ✓ |
| 77، 78 | يمن موبايل | ✓ |
| 10 | يمن فورجي | ✗ بيانات ثابتة |

البادئة **رقمان** بعد `+967` لا ثلاثة. كان التطبيق يقارن ثلاثة أرقام
بخريطة بادئات معكوسة (`77x`←سبأفون، `73x`←يمن موبايل)، فيفشل التصنيف
أو يقع على المشغل الخطأ.

البادئة `10` تخصيص حقيقي لـ **Yemen 4G**، لكنها خدمة بيانات ثابتة
لاسلكية لا شبكة GSM: لا تحمل البوابة شريحة عليها، فهي مُصنَّفة للعرض
والتقارير ومستبعدة من مطابقة «داخل الشبكة» عبر العلم `isMobile` — وإلا
مُنح المنفذ أفضلية 35 نقطة لا يستحقها.

الأسماء تُطبَّع قبل المقارنة: البوابة قد تُعيد «MTN» بينما الوجهة
مُصنَّفة «YOU» وهما المشغل نفسه. المقارنة النصية الخام كانت تفوّت ذلك
فتُهدر ميزة المكالمة داخل الشبكة.

### بوابة البذرة عند الإقلاع

`ensureSeedGateway()` كانت معرَّفة ولا تُستدعى من أي مكان: النشر
أحادي الجهاز يبدأ بسجل أسطول فارغ، فالبوابة المضبوطة في
`red.dinstar.ip` موجودة وتعمل لكن الموزّع لا يراها — يقرأ من
`telecom_gateways` لا من الإعدادات. النتيجة `NO_USABLE_PORT` لكل
مكالمة رغم سلامة الجهاز.

يستدعيها الآن `DinstarFleetBootstrap` عند `ApplicationReadyEvent` لا في
مُنشئ الخدمة: المُنشئ يعمل أثناء بناء السياق وأي استعلام قبل اكتمال
هجرات Flyway يفشل، كما أن التسجيل يُجري فحصًا شبكيًا فتأخيره يمنع
إبطاء الإقلاع. العملية آمنة التكرار، وفشلها لا يمنع الإقلاع لأن بقية
المنصة لا تعتمد على PSTN.

### Asterisk

مع عدة أجهزة لا تكفي وجهة واحدة ثابتة. يمرّر الخادم اسم نظير PJSIP في
المتغيّر `RED_GW`، ويقرؤه الـ dialplan:

```
exten => _X.,1,NoOp(Authorized RED DINSTAR call to ${EXTEN})
 same => n,Set(GW=${IF($["${RED_GW}" != ""]?${RED_GW}:dinstar-gateway)})
 same => n,GotoIf($["${REGEX("^[A-Za-z0-9_-]+$" ${GW})}" = "0"]?badgw)
 same => n,Dial(PJSIP/${EXTEN}@${GW},60)
```

الحارس النمطي ضروري: المتغيّر يدخل سلسلة `Dial`، فاسم غير مقيّد يسمح
بحقن وجهة أخرى. ويُتحقق منه في Kotlin أيضًا قبل الإرسال.

## 6. التعرّف التلقائي

**لا تدعم UC2000 أي بروتوكول اكتشاف بثّي** — لا mDNS ولا SSDP. الادعاء
بغير ذلك تلفيق. الطريقة الموثقة الوحيدة هي فحص نطاق الإدارة باستدعاء
`get_port_info` بمصادقة Digest: الجهاز الذي يرد باستجابة JSON صحيحة
تحمل `error_code=200` وقائمة `info` هو بوابة DINSTAR.

الطراز يُستنتج من قدرات المنافذ عبر حقيقتين تكفيان للتمييز بين
الطرازات الأربعة:

1. **عدد المنافذ التي ردّت** — يفصل الرباعي عن الثماني.
2. **نوع الراديو** لكل منفذ — وجود LTE أو WCDMA يعني المتغيّر ‑T.

إن أفصحت البوابة عن الطراز نصًا في `get_status` فهو أوثق ويُقدَّم.

**تراجع الاكتشاف:** أثناء أول اتصال الطراز مجهول، فيُجرَّب المدى
الأوسع (ثمانية منافذ) أولًا. بعض الإصدارات ترفض الطلب كاملًا إذا تضمّن
منفذًا غير موجود بدل تجاهله، فعند الإخفاق يُعاد الاستعلام بالمدى
الرباعي. بغير هذا التراجع يظهر جهاز رباعي سليم على أنه غير متصل.

**مدى المنافذ لم يعد مثبَّتًا:** كانت `0..7` مكتوبة في ستة مواضع
و`"UC2000-VE-8G"` في ثلاثة، فأي جهاز رباعي يُسجَّل بطراز خاطئ ويُستعلم
عن منافذ لا يملكها. صار المدى مشتقًا من الطراز المكتشَف.

### درجة الثقة — لماذا لا يكفي «ردّ الجهاز»

الردّ على `get_port_info` بمصادقة Digest دليل قوي، لكنه ليس قاطعًا
وحده: خادم وكيل أو جهاز آخر على المنفذ نفسه قد يردّ بمصادفة. وضمّ
جهاز غير مقصود إلى الأسطول **أسوأ من عدم اكتشافه**، لأنه يبتلع
مكالمات حقيقية صامتًا.

لذلك تُجمَّع إشارات مستقلة:

| الإشارة | النقاط | لماذا |
|---|---|---|
| ردّ على `get_port_info` بمصادقة Digest | 45 | تحدّث بالبروتوكول ونجحت المصادقة |
| أفصح عن رقم تسلسلي (`sn`) | 25 | هوية ثابتة يُصدرها الجهاز |
| عنوان MAC ضمن **F8:A0:3D** | 20 | OUI مسجّلة لـ Dinstar في IEEE |
| أنواع الراديو معروفة | 5 | يُبلّغ GSM/WCDMA/LTE لا UNKNOWN |
| ردّ على `get_status` | 5 | إصدار حديث (1102+) |

**حد الضم التلقائي 70** = الردّ + الرقم التسلسلي. الردّ وحده (45) لا
يكفي. ما دون الحد يُعرض على المسؤول ليقرّره يدويًا مع بيان الإشارات
المرصودة.

عنوان MAC **تأكيد لا شرط**: جهاز خلف NAT أو بمحوّل شبكة مستبدل قد لا
يُفصح عنه، ورفضه لذلك يعني تفويت جهاز سليم (يحصل على 80 فيبقى قابلًا
للضم).

### الرقم التسلسلي متاح في كل استجابة

توثيق `get_port_info` (§10.3) ينص على أن **كل استجابة تحمل حقل `sn`**.
كان يُهمَل ويُقرأ التسلسلي من `get_status` وحده — وهو أمر **لا تدعمه
الإصدارات الأقدم من 1102**، فتفقد تلك الأجهزة هويتها الثابتة وتُعرَّف
بعنوانها الشبكي الذي يتبدّل مع DHCP فتتضاعف سجلاتها. الآن يُقرأ من
`get_port_info` أولًا ومن `get_status` تأكيدًا.

### ضوابط الفحص

الفحص **معطّل افتراضيًا**. لا يُطلق خادم مسحًا للشبكة بلا قرار صريح:

```yaml
red:
  dinstar:
    discovery:
      enabled: ${DINSTAR_DISCOVERY_ENABLED:false}
      subnets: ${DINSTAR_DISCOVERY_SUBNETS:192.168.11.0/24}
```

وعند تفعيله تبقى الحدود:

- **عناوين خاصة فقط** (RFC 1918) — يُرفض أي نطاق عام.
- **الأقنعة ‎/24 إلى ‎/30 فقط** — ما هو أوسع يعني آلاف الطلبات.
- **254 عنوانًا كحد أقصى** لكل عملية.
- **مهلة قصيرة** (ثانيتان) لعملاء الفحص: عنوان بلا جهاز يجب أن يسقط
  بسرعة وإلا استغرق مسح ‎/24 دقائق.
- تفرّع محدود بـ 32 خيطًا حتى لا تُغرَق شبكة الإدارة.

```bash
POST /api/admin/dinstar/fleet/discover
{ "subnets": ["192.168.11.0/24"], "adopt": true, "siteLabel": "صنعاء — المقر" }
```

`adopt: false` (الافتراضي) يعرض النتائج دون تسجيل — للمراجعة قبل الضم.

جهازًا سليمًا من التوجيه.

البوابة `OFFLINE` تخرج من الترشيح، لكنها تبقى في السجل ويُعاد فحصها.

له. يتحقق من ذلك فحص آلي.

## 10. تطبيق أندرويد

حمل التطبيق النسخة نفسها من العطل: `DinstarPort.signalPercent` عدد غير
قابل للعدم بقيمة افتراضية `0`، و`isAvailable` يشترط `signalPercent >= 20`
محسوبة من القراءة المغلوطة، و`bestPortForCall` يرتّب بها. صار:

- الحقول `signalPercent` و`signalDbm` و`signalRaw` **قابلة للعدم**، مع
  `signalUsable` منفصل. الخادم هو مرجع التفسير ولا يُعيد التطبيق
  الحساب حتى لا يتفرّع منطقان.
- `isAvailable` يعتمد `signalUsable`، و`bestPortForCall` يرتّب بالـ dBm.
- `isRegisteredButUnusable` يُظهر الشرائح المسجّلة بلا إشارة صالحة.
- `averageSignalDbm` يستبعد ما لا قياس له بدل احتسابه صفرًا.
- `DinstarFleetStatus` جديد: النموذج السابق كان بوابة واحدة، فلم يكن
  ممكنًا عرض جهازين أو معرفة أيّهما حمل المكالمة. الشاشة تستدعي
  `/fleet/ports` بدل `/status`.
- أحداث WebSocket تحمل `gatewayId`: بدونه لا يُعرف أي جهاز تغيّر منفذه.
  و`optInt` استُبدلت بفحص `isNull` صريح لأن `0` قراءة صالحة تعني
  ‎-113 dBm، والخلط بينها وبين الغياب هو أصل العطل نفسه.

كذلك حُذفت `admin_dashboard/src/pages/tabs/DinstarTab.tsx`: نسخة ميتة
لا يستوردها شيء، تكرّر صفحة `DinstarControl` الحيّة وتحمل عطل الإشارة
وخريطة البادئات المعكوسة. إبقاؤها يعني أن يُحيي أحدهم المنطق المعطوب.

## 11. الإعداد

```yaml
red:
  dinstar:
    ip: ${DINSTAR_IP:192.168.11.1}      # بوابة البذرة
    port: ${DINSTAR_PORT:443}
    scheme: ${DINSTAR_SCHEME:https}
    username: ${DINSTAR_USERNAME:admin}
    password: ${DINSTAR_PASSWORD:admin}  # غيّرها — لا تترك الافتراضي
    connect-timeout-seconds: 5
    read-timeout-seconds: 10
    probe-timeout-seconds: 2
    discovery:
      enabled: false
      subnets: ''
```

**قبل التشغيل:**

1. غيّر كلمة مرور واجهة الجهاز من الافتراضية.
2. اعزل شبكة الإدارة (VLAN مستقلة) — القبول العمياء لشهادة TLS مبني
   على هذا الافتراض.
3. عرّف نظير PJSIP لكل جهاز في Asterisk وسجّل اسمه في `pjsipEndpoint`.
4. تحقق بـ `POST /fleet/probe` قبل التسجيل.
