# تشخيص أولي مؤكد: DINSTAR / PSTN / SMS / المكالمات

**الحالة:** تدقيق المصدر جارٍ؛ هذه النتائج مستندة إلى مسارات حية في `red-app` و`backend-server` و`pstn-asterisk`، وليست حكماً على حالة SIM أو الشبكة قبل قراءة الجهاز الفعلية.

## تعريف جهاز المشروع المقصود

توثق ملفات المشروع الجهاز المستهدف على أنه **DINSTAR UC2000-VE-8T**: بوابة 8 قنوات GSM/3G/4G/LTE/VoLTE بحسب متغير المودم الإقليمي، وتحول SIP/RTP إلى الشبكة الخلوية والعكس. كما يعرف الخادم صراحةً العائلة `UC2000-VE-4G/8G/4T/8T` ويمنع افتراض توافق المشغل من الموديل وحده.

| حقيقة تقنية | مصدر المشروع | المصدر الخارجي الأولي |
|---|---|---|
| الصوت يمر عبر Backend → Asterisk AMI → PJSIP → DINSTAR؛ وليس عبر endpoint HTTP مخترع | `DinstarHardwareService.initiateCall` | [1] [2] |
| HTTP API يستخدم للمراقبة وSMS/USSD/المنافذ وCDR وفق firmware | `DinstarHardwareService` | [2] [3] |
| متغير T قد يدعم LTE/VoLTE، لكن النطاقات والـ firmware والتسجيل الحي حاسمة | `DinstarModelProfile` | [1] [2] |

## أسباب مؤكدة تمنع الاستقبال أو تجعل أزرار الاتصال غير فعالة

| الطبقة | الخلل | الأثر الفعلي | المعالجة التي بدأت |
|---|---|---|---|
| Android WebSocket | الخادم يرسل `{type,data}`، بينما `PstnEventSocket` كان يفك الحقول من الجذر | `SMS_RECEIVED` و`SMS_STATUS` و`PSTN_INCOMING` تصل بلا بيانات نافعة وتُهمل | إضافة محلل `PstnEventEnvelopeCodec` واختبارات عقد |
| Android lifecycle | اتصال `/ws/pstn` كان يبدأ عند فتح شاشة SMS فقط | لا تظهر مكالمة DINSTAR واردة إذا لم تكن شاشة SMS مفتوحة | إضافة `PstnIncomingCallCoordinator` يبدأ بعد المصادقة |
| Android incoming UI | `IncomingCallViewModel` أنشأ `PstnEventSocket` ثم أرسل قبول/رفض من دون `connect()` | أزرار القبول والرفض قد ترسل إلى socket غير مفتوح | تهيئة socket عند ربط Intent للمكالمة |
| Android admin socket | `DinstarViewModel` ينتظر `PstnIncoming` من `/ws/dinstar`، لكن هذا الجسر لا يصدره ولا يفسره | مسار استقبال ميت؛ لا يصل event إلى الشاشة | توحيد استقبال المستخدم على `/ws/pstn` |
| الخادم → Android | payload الوارد استخدم حقل `gateway` لقناة Asterisk بدل `channel` | لا يملك Android القناة اللازمة للقبول أو الرفض | تغيير الحدث إلى `channel` مع توافق انتقالي للعميل |
| WebSocket authorization | قبول/رفض PSTN لم يتحقق من أن session يملك المكالمة الواردة | مستخدم PSTN مصادق آخر يستطيع محاولة التحكم بقناة لا تخصه | ربط event بالمستلمين المصرح لهم وclaim ذري لأول قبول |
| الصوت الوارد | بعد قبول channel يوجه Asterisk إلى endpoint ثابت `red-webrtc-client`، لكن Activity لا يسجل عميل SIP/WebRTC قبل التحويل | حتى مع وصول الشاشة، الصوت الوارد قد لا يُنشأ أو لا يصل للتطبيق | قيد هندسي قيد المعالجة: تسجيل SIP لكل مستخدم وتهيئة incoming bridge قبل redirect |
| الإشعار بالخلفية | الخادم ينشئ إشعاراً داخلياً، لكنه لا يوقظ تطبيقاً مقتولاً فعلياً بلا FCM token و`FCM_V1_SERVICE_ACCOUNT` | لا يرن التطبيق في الخلفية أو بعد الإنهاء | يتحقق لاحقاً عبر صلاحية الإشعارات وFCM وforeground behavior |

## أثر متوقع على الاتصال الصادر

المشروع يملك **مسارين متوازيين** للمكالمة الهاتفية: مسار AMI مباشر (`/api/pstn/calls`) ومسار WebRTC bridge (`/api/pstn/bridge`). المسار المباشر يطلب من Asterisk إنشاء `Local/<number>@from-red-backend` ثم يطلب `Dial(PJSIP/<number>@gateway)`؛ لا ينشئ ذلك بذاته صوتاً بين التطبيق وAsterisk. مسار bridge يحتوي WebRTC/SIP client لكنه يعتمد endpoint ثابتاً مشتركاً `red-webrtc-client`، وهو غير مناسب لتوجيه وارد متزامن متعدد المستخدمين.

لذلك سيُوحد الإصلاح على عقد واحد لكل حالة: صلاحية المستخدم → حجز منفذ → تسجيل SIP/WebRTC للمستخدم → Asterisk originate/redirect → أحداث مرتبطة بـ callId → تحرير موثوق. لا تُفعل مكالمة حية قبل التحقق من SIP registration وcodec/RTP وNAT على الجهاز الفعلي.

## حالة SMS

تنفيذ HTTP API في الخادم يدعم إرسال SMS واستقبالها والاستعلام عن queue والـ delivery status، ويترجم `GSM7BIT/UCS2` إلى قيم DINSTAR المناسبة (`gsm-7bit/unicode`). أبرز الثغرة المكتشفة في تجربة المستخدم كانت غلاف WebSocket المذكور أعلاه؛ لذلك لم تكن التحديثات الحية مضمونة. يبقى التدقيق التالي: دقة تقسيم Unicode إلى أجزاء، ربط delivery report برسالة محددة لا برقم فقط، ملكية الرسائل الواردة لكل منفذ/مستخدم، ومعالجة صفوف الجهاز التالفة من دون تعطيل دفعة ingest كاملة.

## ما لا يمكن تقريره بعد

لا يمكن الجزم بأن الجهاز يحتاج تغييراً أو أن SIM/الشبكة سبب الفشل قبل جمع قراءة حيّة من `get_port_info` وSIP registration والـ firmware والمتغير الراديوي. جهاز UC2000-VE-8T قد يكون مناسباً إن كانت نطاقات الراديو وVoLTE وSIM وSIP trunk متوافقة؛ استبداله ليس إجراءً صحيحاً قبل هذا الإثبات.

## تحقق إضافي من الخلفية والإشعارات

فحص `AndroidManifest.xml` يؤكد وجود صلاحيات الإشعارات والمكالمات و`IncomingCallActivity` والخدمات الأمامية وقناة `red_calls_incoming`. لكنه لا يعرّف `FirebaseMessagingService` أو أي مستقبل inbound data-push. يوجد `VoipPushRegistrar` لتسجيل token فقط؛ لذلك لا يمكن أن يوقظ التطبيق المقفَل/المغلق عبر FCM من دون إضافة خدمة استقبال وتهيئة Firebase وحساب خدمة على الخادم. هذه ليست مشكلة في UC2000-VE، بل فجوة مستقلة في طبقة التسليم إلى الجهاز.

> لا يُفعّل FCM أو يُضاف حساب خدمة ضمن هذه الجولة قبل توفير إعداد staging منفصل وآمن، لأن ذلك يتطلب بيانات اعتماد خارجية واختبار جهاز حقيقي.

| حالة التطبيق | المسار المتاح الآن | النتيجة المتوقعة قبل استكمال FCM |
|---|---|---|
| في المقدمة ومصادق | `/ws/pstn` عبر المنسق المركزي | يمكن استقبال عرض المكالمة بعد إصلاح عقد الحدث |
| بالخلفية والخدمة الأمامية حية | قد يبقى WebSocket نشطاً حسب سياسة Android والشبكة | يحتاج اختبار جهاز حقيقي |
| مقتول/مقيّد بالخلفية | لا توجد خدمة FCM inbound معلنة | لا ضمان لإيقاظ التطبيق أو إظهار شاشة الاتصال |

## القرار الهندسي المؤقت

يجب عدم استبدال UC2000-VE بسبب مشكلة background delivery. أولوية الإصلاح هي إكمال جسر SIP/WebRTC الوارد والمكالمات الصادرة في التطبيق، ثم إضافة استقبال FCM حقيقي واختبار المسارات على جهاز Android. يقرر تغيير الجهاز فقط بعد فشل اختبارات SIP registration وSIM registration وRTP/codec مع firmware ومودم متوافقين.

## نتائج البحث الخارجي الموثقة

تؤكد صفحة DINSTAR الرسمية لـ UC2000-VE أنه جهاز **4 أو 8 قنوات** للصوت وSMS بين GSM/WCDMA/LTE وSIP، مع VoLTE، SIP v2/RFC3261، RTP، وتسجيلات CDR وHTTP API للـ SMS. وهذا يطابق تصميم المشروع: **الصوت عبر SIP/Asterisk** وعمليات SMS/USSD عبر HTTP API، ولا يدعم افتراض أن endpoint HTTP عام يجب أن ينشئ مكالمة صوتية مستقرة.

كما تؤكد إرشادات DINSTAR أن مفاهيم الربط مع Elastix تنطبق على Asterisk وFreeSWITCH و3CX وIssabel، أي أن تشخيص التسجيل (REGISTER/endpoint/route) والـ codecs وRTP/NAT هو المدخل الصحيح. دليل DINSTAR لتحليل HTTP API ينبه أيضاً أن اختيار channel في SMS/USSD قد لا يظهر مباشرة في HTTP log ويجب التحقق من `port_map` وlogs على الجهاز؛ لذلك لا تُفسر رسالة SMS ناجحة وحدها كدليل على أن المنفذ المقصود أو مسار الصوت صحيح.

مصادر مجتمعات Asterisk وPBX غير الرسمية أضافت فرضيات قابلة للاختبار فقط: فشل المكالمة الخارجة مع تسجيل سليم قد ينشأ من endpoint/route أو SIP 503، وفشل اتجاه الصوت غالباً يرتبط بـ NAT/firewall/RTP. لا تُعد هذه تشخيصاً لجهاز RED قبل قراءة SIP trace وRTP/AMI logs الفعلية.

| نتيجة البحث | أثرها على RED |
|---|---|
| UC2000-VE يدعم SIP/RTP وSMS وHTTP API وVoLTE بحسب المتغير | الجهاز مناسب مبدئياً؛ لا يوجد سبب هندسي فوري لاستبداله |
| توافق LTE يعتمد على region/radio variant وSIM والتسجيل الحي | يلزم قراءة label/firmware و`get_port_info` وSIP registration |
| SMS/USSD قد يمران عبر channel مختلف لا يظهر صراحة في HTTP request | يلزم ربط port/task/response والتحقق من logs للجهاز |
| SIP/RTP/NAT/codec هي محاور تشخيص مسارات الصوت | تستكمل بخطة capture وسيناريو منفذ واحد قبل الإنتاج |

**مصادر:** صفحة المنتج الرسمية [UC2000-VE](https://www.dinstar.com/GSM-3G-LTE-voip-gateway/4-8-ports/)، وإرشاد [الربط مع Elastix/Asterisk](https://www.dinstar.com/blog/technical-guide/configuration-video-of-UC2000-with-Elastix/)، وإرشاد [تحليل channel في HTTP API](https://www.dinstar.com/blog/technical-guide/how-to-analyze-which-channel-is-included-in-http-api-log/).

## إصلاح إضافي في ingest الرسائل الواردة

تمت معالجة خطأ في `SmsService`: كان صف JSON ناقص من الجهاز يتحول إلى النص الحرفي `"null"`، وقد يتسبب رقم غير صالح في استثناء يوقف معالجة الدفعة الواردة. أصبح التحليل يتجاهل الصف الناقص أو الرقم غير الصالح ويسجل تحذيراً، بينما يستمر في تخزين الرسائل السليمة في الدفعة نفسها. هذا لا يغير رقم الرسالة أو يرسل SMS؛ إنه يعزز مقاومة المعالجة لردود firmware المتباينة.

## تحقق حي من شبكة الجهاز — قراءة فقط

أُجري فحص قراءة فقط من Windows المتصل محلياً في **2026-08-21**. النتيجة تثبت أن جهاز UC2000 متاح على `192.168.11.1`: ICMP ينجح وTCP/80 مفتوح. لا يثبت هذا تسجيل SIP أو جاهزية SIM، لكنه ينفي انقطاع الكهرباء أو الكابل كسبب أولي. ظهرت على Windows واجهتا IPv4 ضمن نفس النطاق: `192.168.11.105/24` على واجهة `kk` و`192.168.11.131/24` على Wi‑Fi، وهي حالة يجب ضبطها قبل الاعتماد على مسار واحد ثابت للبوابة.

| فحص قراءة فقط | النتيجة | الدلالة |
|---|---:|---|
| Ping `192.168.11.1` | ناجح | الجهاز متصل ويجيب |
| TCP/80 | مفتوح | واجهة HTTP الإدارية متاحة |
| TCP/443 | مغلق | لا ينبغي افتراض HTTPS حتى تثبيته من إعداد الجهاز |
| TCP/5060 وTCP/5062 | مغلقان | لا يثبتان فشل SIP لأن المشروع يستخدم UDP؛ يلزم فحص UDP/تسجيل PJSIP وlogs |

> ملاحظة: فحص TCP لمنفذي 5060/5062 ليس اختباراً صحيحاً لصحة SIP/UDP. المرحلة التالية تقرأ تسجيل PJSIP وSIP trace بشكل آمن؛ ولا تغير أي إعداد أو route في UC2000.

## نتيجة حاسمة: هوية العنوان المهيأ للجهاز غير مثبتة

بعد نجاح ping وHTTP على `192.168.11.1`، قُرئت **صفحة الدخول العامة فقط** بلا اسم مستخدم أو كلمة مرور. عنوان الصفحة هو **`4G CPE`**، ولم يظهر `UC2000` أو `DINSTAR` في التعريف العام. لذلك لا يصح اعتبار `DINSTAR_IP=192.168.11.1` دليلاً على أن هذا هو UC2000-VE؛ من المرجح أن المشروع يشير إلى CPE/راوتر 4G مختلف أو أن الهوية العامة للجهاز لا تطابق الافتراض في الإعداد.

| حقيقة مثبتة | ما لا تثبته |
|---|---|
| `192.168.11.1` يرد ويعرض HTTP/80 | أنه UC2000-VE |
| صفحة الدخول عنوانها `4G CPE` | نوع المودم أو firmware أو SIP registration |
| TCP/443 وTCP/5060 وTCP/5062 مغلقة | أن SIP/UDP متوقف؛ يلزم فحص UDP وPJSIP/AMI |

> لا تُغير `DINSTAR_IP` ولا تسجل دخولاً ولا تعيد تشغيل أي جهاز قبل مطابقة MAC/vendor أو اكتشاف UC2000 من شبكة الإدارة أو صفحة حالة مصادق عليها. هذه النتيجة وحدها قد تفسر فشل كل HTTP API وSIP المتوقعين في المشروع.

## عنوان UC2000 الحقيقي المحتمل على شبكة الإدارة

أظهر فحص سلبي لاحق للجيران المعروفين أن `192.168.11.2` يستجيب على HTTP/80 بتحويل `302` مع cookie باسم **`devckie`** وخادم `MatrixSSL`، وهي بصمة تتطابق مع منطق جلسة واجهة DINSTAR الذي يستخدمه `DinstarHardwareService` في المشروع. في المقابل، `192.168.11.1` يعرض صفحة `4G CPE`. لذلك أقوى فرضية حالياً هي:

| العنوان | الدليل غير المصادق | التفسير |
|---|---|---|
| `192.168.11.1` | صفحة دخول بعنوان `4G CPE` وعنوان MAC `00-0A-13-43-59-B0` | جهاز CPE/راوتر، **وليس** هدف UC2000 المفترض |
| `192.168.11.2` | HTTP 302، cookie `devckie`، `MatrixSSL/4.3.0-OPEN` | مرشح قوي جداً لواجهة DINSTAR/UC2000 |

هذا يفسر لماذا فشل المشروع، الذي افترض `DINSTAR_IP=192.168.11.1`: خادم الخلفية وAsterisk قد يحاولان HTTP/SIP إلى CPE بدلاً من UC2000 الحقيقي. لا يعدل التقرير `.env` أو الجهاز؛ سيُستكمل التحقق بقراءة صفحة DINSTAR/API غير مصادقة وتسجيل PJSIP قبل أي تصحيح إعداد.

### تأكيد API للعنوان المرشح

طلب GET غير مصادق إلى `https://192.168.11.2/api/get_port_info` أعاد **`401 Unauthorized`** مع `WWW-Authenticate: Digest` وcookie `devckie` وخادم `MatrixSSL`. هذا هو السلوك المتوقع لواجهة API في UC2000 مع عدم إرسال أي بيانات اعتماد، ويؤكد أن `.2` هو جهاز DINSTAR قابل للوصول، بينما `.1` هو عنوان خاطئ للبوابة في إعداد المشروع. ظهر أيضاً في صفحة الدخول العامة إصدار واجهة `04240302`، لكنه **ليس** إصدار firmware كاملاً ولا ينبغي استخدامه لاختيار ملف upgrade.

**الاستنتاج التشغيلي:** سبب فشل الاتصال لا يبدأ من عطل عتادي مثبت؛ تكامل الخلفية موجه إلى IP جهاز CPE (`.1`) بدلاً من DINSTAR (`.2`). يقتصر التصحيح التالي على إعداد staging/بيئة محلية متحكم بها بعد نسخ `.env` احتياطياً، ثم تحقق من `get_port_info` وPJSIP registration قبل محاولة مكالمة أو SMS.

## تصحيح بعد فحص البيئة والحاوية الفعلية

فحص `.env` الحالي (مع حجب الأسرار) يثبت أن التشغيل الحي **لا يستخدم** القيمة الافتراضية القديمة `.1`: القيم الفعلية هي `DINSTAR_IP=192.168.11.2` و`DINSTAR_PORT=443` و`DINSTAR_SCHEME=https` و`DINSTAR_IPS=192.168.11.2`. كما أن Asterisk يرى contact ثابتاً إلى `sip:192.168.11.2:5062` بحالة **Avail**، ويرى تسجيل منفذ DINSTAR إضافياً على UDP/5060 بحالة **Avail**. لذلك لا ينبغي وصف `.1` بأنه العنوان الجاري في `.env`؛ الخلل هو أن scripts/docs الافتراضية ما زالت تشير إليه وقد تقود إلى إعادة إعداد خاطئة لاحقاً.

أما endpoint `red-webrtc-client` في Asterisk فحالته **Unavailable**. هذه نتيجة متوافقة مع تشخيص مسار الصوت: UC2000/Asterisk قابلان للوصول، لكن تطبيق Android لا يبقي SIP/WebRTC client مسجلاً لاستلام تحويل المكالمة الواردة، ولا يربط المسار المباشر للصادر بصوت التطبيق.

| الطبقة | الحالة الحية | الاستنتاج |
|---|---|---|
| UC2000 HTTP API على `.2` | قابل للوصول مع HTTP Digest | الجهاز متاح |
| Asterisk → UC2000 PJSIP `.2:5062` | Avail | مسار SIP إلى البوابة قائم |
| DINSTAR port REGISTER → Asterisk UDP/5060 | Avail | مسار وارد من الجهاز قائم مبدئياً |
| `red-webrtc-client` | Unavailable | سبب ملموس لفشل ربط الصوت/الاستقبال في التطبيق |

> الإصلاح لا يتطلب تبديل UC2000. الأولوية هي إزالة الافتراض القديم `.1` من scripts/docs، وتصحيح دورة تسجيل WebRTC/SIP وتوجيه الصوت للمستخدم في التطبيق.
